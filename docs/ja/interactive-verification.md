# 対話の画面での検証の基盤

> [!IMPORTANT]
> この文書は、このリポジトリの開発とテストのための道具を説明します。サーバーを使う利用者には不要です。基盤は、配布物 (`dist/` の実行ファイル、スキル) に含めません。

エージェントの CLI (Claude Code、Codex、Copilot CLI、Grok、agy) の対話の画面を、仮想端末の上で起動し、指示を送り、画面の内容から結果を判定します。各 CLI の非対話の実行では確かめられない動作 (指示を待っている間に届く通知の見え方、複数回のやりとり、起動し直した後の再参加、指示ファイルの効き方) を、利用者の手作業なしに、繰り返し確かめられます。

## 用途

- CLI の版が上がったときに、サーバーとの組み合わせでの動作を確かめ直す。
- サーバーの案内 (`lounge_help`、接続時の案内文、ツールの説明文) を変えたときに、エージェントの動作がどう変わるかを確かめる。
- 利用ガイドの「検証済みの範囲」の根拠を作る。

## 前提

| OS | 必要なもの |
|---|---|
| Linux、WSL | Python 3.10 以降 (標準ライブラリだけを使います)、確かめる CLI、サーバーの実行ファイル |
| Windows | Python 3.10 以降、ライブラリ `pywinpty` (`python -m pip install --user pywinpty`)、確かめる CLI、サーバーの実行ファイル (`windows-amd64`) |

基盤は、OS ごとに、その OS の Python で独立して動きます。Windows の側の確認に、WSL は要りません。

各 CLI は、ログインを済ませ、既定のモデルで使える状態にしておきます。シナリオ 4 の実行ファイルを作るには、Go が要ります ([手順](#手順))。

## 構成

```text
scripts/interactive/
    verify.py              入口 (run、build-test-server、summary)
    harness/
        terminal.py        仮想端末の共通の部分と、OS による選択
        terminal_posix.py  Linux と WSL の実装 (標準の pty モジュール)
        terminal_windows.py  Windows の実装 (pywinpty)
        screen.py          出力の加工、端末の画面の再現、文字列の照合
        agents.py          CLI ごとの定義と、CLI の操作
        server.py          サーバーの起動と停止、接続の診断の読み取り
        lounge.py          相手役のセッション (MCP を HTTP で呼ぶ小さなクライアント)
        report.py          結果の記録
        scenarios/         シナリオ
    tests/                 自己試験 (CLI の代わりの小さなプログラムを使います)
```

Figure: 基盤のファイルの構成

OS によって異なるのは、仮想端末を扱うモジュールと、プロセスへの信号の送り方だけです。他の部分は、すべての OS で共通です。

### 判定の方法

- 画面: CLI の出力を、端末の画面として再現します (カーソルの移動、消去、スクロール、代替画面)。画面から消えた行は、履歴として残します。変わった部分だけを描き直す CLI でも、画面に表示された文字を読めます。
- 応答の完了: 指示のたびに、乱数の語を小文字で示し、「応答の最後に、大文字で書く」ように求めます。大文字の語は指示の表示に現れないため、その語が画面に現れたことで、応答を書き終えたと判定します。その後、文字が書かれない状態が 4[秒] 続くのを待ちます (考えている途中に語を表示する CLI があるためです)。記号だけの描き直し (待機中のアニメーション) は、書かれた文字に数えません。
- 合否: 画面の内容と、サーバーの接続の診断 (`--log-connections`。どの接続が、いつ、どのツールを呼んだか) と、データベースの内容 (送達状態、セッションの一覧) を組み合わせて決めます。

### 確認用の環境

- 実行のたびに、確認用のフォルダー (既定は、OS の一時フォルダーの下の新しいフォルダー) を作ります。データベース、CLI の作業フォルダー、画面の記録、結果は、その中に置きます。リポジトリの中には、Python が作る `__pycache__` (Git の無視の対象) のほかは、何も作りません。
- サーバーは、ループバックの別のポート (既定は `127.0.0.1:7799`) で起動します。そのアドレスで、すでに別のサーバーが応答する場合は、起動せずに、シナリオを `unverified` にします。
- CLI には、確かめる前に、`agent-lounge` の名前でサーバーを登録し、終わると解除します。すでに `agent-lounge` の名前の登録がある CLI と、登録の一覧を取得できない CLI は、登録を変えずに飛ばします。
- 許可は、起動のオプションで先に与えます (agent-lounge のツールと、作業フォルダーへの書き込み)。許可を求める画面には応答しません。CLI の起動時の確認 (作業フォルダーを信頼するかどうか、端末の設定を変えるかどうか) にだけ応答します。
- Copilot CLI には、シェルのコマンドをすべて許可します (`--allow-tool shell`)。プロフィールの値を調べるコマンドを、モデルが実行のたびに選ぶため、コマンドを個別に許可する方法では、許可の確認の画面で止まります。この許可は、確認用のフォルダーの中に限定されません。Copilot CLI は、基盤を実行したユーザーの権限で、任意のコマンドを実行できます。
- CLI に渡す環境変数 `PWD` は、CLI の作業フォルダーにします。
- 基盤を動かすセッションの環境変数のうち、CLI の動作を変えるもの (`CLAUDE` で始まるもの、エディターの端末の変数など) は、CLI に渡しません。

## 手順

### 自己試験

CLI もサーバーも使わずに、基盤そのものを確かめます。CI でも、Linux で実行しています。

```sh
python3 -m unittest discover -s scripts/interactive/tests
```

Windows では、`python3` を `python` に置き換えます。

### シナリオ 4 の実行ファイルを作る

シナリオ 4 は、接続時の案内文に合言葉を足したサーバーを使います。リポジトリのソースを一時フォルダーに複製して作るため、リポジトリは変わりません。作った実行ファイルは、確認だけに使い、配布しません。

```sh
python3 scripts/interactive/verify.py build-test-server --out /tmp/iv/test-server
python3 scripts/interactive/verify.py build-test-server --goos windows --out /tmp/iv/test-server.exe
```

合言葉は、実行ファイルと同じ場所の `<実行ファイル>.json` に書かれます。Windows の側には Go がない場合が多いため、Windows 向けの実行ファイルは、Go のある環境で作って、Windows の側に複製します。CPU の種類は、`--goarch` で指定します (既定は `amd64`)。

### シナリオを実行する

```sh
python3 scripts/interactive/verify.py run --server dist/agent-lounge-mcp --test-server /tmp/iv/test-server
```

| オプション | 内容 |
|---|---|
| `--server` | 確かめるサーバーの実行ファイル (必須) |
| `--test-server` | シナリオ 4 の実行ファイル。省くと、シナリオ 4 を飛ばします |
| `--agents` | 確かめる CLI (`claude`、`codex`、`copilot`、`grok`、`agy` をカンマで区切る)。既定は、すべて |
| `--scenarios` | 実行するシナリオの番号 (カンマで区切る)。既定は、すべて |
| `--listen` | 確認用のサーバーのアドレス。既定は `127.0.0.1:7799` |
| `--out` | 確認用のフォルダー。既定は、一時フォルダーの下の新しいフォルダー |

Table: run のオプション

1 つの CLI で、すべてのシナリオに 10[分] ほどかかります。CLI ごとに、各シナリオの開始と結果を、標準出力に 1 行ずつ表示し、最後に、すべての結果を JSON で表示します。

`summary` は、確認用のフォルダーの結果を、もう一度表示します。

```sh
python3 scripts/interactive/verify.py summary <確認用のフォルダー>
```

## シナリオ

指示文は英語です。セッション名は `iv-<CLI の短い名前>` です。

| 番号 | 名前 | 内容 | 対象 |
|---|---|---|---|
| 1 | `shutdown-notice` | 参加した後、指示を待っている間にサーバーを止めます。20[秒] の間の画面と、次の指示 (ツールを呼ばずに、サーバーから知らせを受けたかを答える) への応答から、停止の知らせが画面とモデルに届いたかを記録します。接続の診断から、ログのレベルの設定と、停止の通知を送ったかを記録します | 5 つの CLI |
| 2 | `several-instructions` | 参加した後、相手役がメッセージを送り、次の指示で受信箱を読ませます。応答にメッセージの合言葉があり、送達状態が受け取り済みであれば合格です | 5 つの CLI |
| 3 | `join-again` | 参加した後、CLI を終了し、相手役がメッセージを送ります。CLI を起動し直して、同じ名前で参加し直させます。応答に合言葉があり、セッションが増えていなければ合格です | 5 つの CLI |
| 4 | `server-instructions` | 合言葉を案内文に足したサーバーで、ツールを呼ばずに合言葉を答えさせます。CLI が接続時の案内文をモデルに渡しているかを記録します | 5 つの CLI |
| 5 | `instruction-files` | 候補の指示ファイル (`AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`GROK.md`、`.github/copilot-instructions.md`) に別々の合言葉を書き、CLI がどのファイルを読むかを記録します。答えがない場合は、新しいセッションで 1 回やり直します。次に、読むファイルに `lounge_help` の「指示ファイルに貼る文面」を置き、チャットと関係のない作業 (`notes.txt` を作って読み返す) を 3 回指示して、参加、作業の前後の受信箱の確認、メモリの検索を行った回数を記録します | 5 つの CLI |
| 6 | `token-stopped` | トークンを必須にしたサーバーに、トークンを付けて登録し、参加できることを確かめた後、トークンを再発行します。非対話の実行で、CLI が利用者に何を伝えるか (認証の失敗か、OAuth の認証の流れを始めたか、時間の上限までに終わったか) を記録します。登録を解除した後、CLI の設定と履歴のフォルダーに、トークンが残っていないかを調べます | Codex、Copilot CLI、agy |

Table: シナリオ

シナリオ 1、4、5 は、合格と不合格を付けず、結果を記録します。エージェントの動作は、CLI とモデルで決まり、このリポジトリでは変えられないためです。

## 結果の読み方

確認用のフォルダーの `<番号>-<名前>/<CLI>/` に、次のファイルを置きます。

| ファイル | 内容 |
|---|---|
| `result.json` | 結果。`status` は `done` (すべての手順を実行した。値は `values`)、`unverified` (基盤が CLI を操作できなかった、または判定できなかった。理由は `reason`)、`skipped` のどれか |
| `screen.txt` など | 画面の記録 (端末の画面を再現したもの) |
| `server.log` | サーバーの標準エラー (接続の診断を含む)。シナリオ 1 から 3 では、結果と同じ場所。どのシナリオでも、サーバーごとのフォルダー (`server/`、`discovery/`、`run<番号>/`) に、データベースと並べて置きます |
| `error.txt` | 基盤の例外の記録 (起きた場合だけ) |

`values` の主な項目は、次のとおりです。

| 項目 | シナリオ | 内容 |
|---|---|---|

## CLI の定義の直し方

CLI の画面が版によって変わり、基盤が操作できなくなった場合は、`scripts/interactive/harness/agents.py` の定義を直します。シナリオは変えません。

| 項目 | 内容 |
|---|---|
| `interactive` | 対話の画面の起動のオプション (先に与える許可を含む) |
| `one_shot` | 指示を 1 回だけ実行して終わる起動 (シナリオ 6) |
| `register`、`unregister`、`list_servers` | サーバーの登録、解除、一覧のコマンド |
| `ready` | 指示を受け付ける状態になったことを示す文字列 (どれか 1 つが画面にあればよい) |
| `dialogs` | 起動時の確認の画面の文字列と、それに答えるキー |
| `quit_keys` | 終了のキー |
| `instruction_files` | その CLI が読む指示ファイル (シナリオ 5 で、文面を置くファイルを選ぶ順) |
| `settings`、`settings_option` | 起動のたびに書く設定ファイルの内容と、それを渡すオプション (agy の、ツールの許可) |

Table: CLI の定義の項目

`result.json` の `reason` が `the harness could not drive the CLI` で始まる場合は、`reason` に続く画面の内容から、準備ができた目印や確認の画面の文字列が変わっていないかを確かめます。

## 制限事項

- 基盤は、端末の画面を、よく使われる制御だけで再現します。色、文字の装飾、マウス、一部の画面の制御は扱いません。判定は、画面に表示された文字列の有無だけで行います。
- エージェントの応答は、実行のたびに変わります。結果は、その時点の CLI の版とモデルでの記録です。
- 許可を求める画面には応答しません。先に与えた許可で足りない操作をエージェントが行うと、応答が完了せず、時間切れになります。
- Claude Code (2.1.327) は、Claude Code のセッションの作業用の一時フォルダーの下にある `CLAUDE.md` を読みません。Claude Code のセッションから基盤を実行する場合は、確認用のフォルダー (`--out`) を、その外に置きます。
- モデルが、指示ファイルの内容を答えるのを断ることがあります (Copilot CLI)。やり直しても答えがない場合、シナリオ 5 は `unverified` になります。
- CLI は、起動のときに、自分で版を上げることがあります。結果の `environment` の版は、各シナリオの前に調べた値です。
- シナリオ 4 と 5 の判定は、合言葉を答えるかどうかで行います。エージェントが合言葉を答えない理由 (読んでいない、読んだが答えない) は区別しません。シナリオ 5 では、「ツールを呼ばない」という指示にエージェントが従ったかどうかを確かめません。エージェントがフォルダーのファイルを自分で読んで答えた場合も、「CLI が読むファイル」に数えます。
- 入力した指示が画面に出ない場合は、指示を打ち直します。入力欄は消さないため、指示の一部だけが落ちた場合は、指示が重なって送られます。
- シナリオ 2 と 3 で、応答が時間の上限までに終わらず、合格の条件も満たさない場合は、不合格ではなく `unverified` にします。
- CI では、自己試験だけを実行します。シナリオの実行には、各 CLI のログインと利用量が要ります。
- macOS では、確かめていません。
