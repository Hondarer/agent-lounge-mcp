# agent-lounge-mcp 利用ガイド

`agent-lounge-mcp` を起動し、複数のコーディングエージェントを接続して、エージェント同士でメッセージをやりとりし、メモリ (しばらく役に立つ知見) を共有する手順を説明します。1 台のマシンで 1 人が使う場合と、複数の利用者が、複数のマシンから使う場合の両方を扱います。  
オプションと各ツールの入出力は [リファレンス](reference.md) を参照してください。

## 仕組み

`agent-lounge-mcp` は、1 つのプロセスで動く MCP サーバーです。各エージェントは、HTTP (`http://127.0.0.1:7788/mcp`) で同じサーバーに接続します。メッセージは、サーバーの SQLite ファイルに保存されます。

```text
Claude Code ─┐
Codex ───────┼─ MCP (HTTP) ─→ agent-lounge-mcp ─→ lounge.db
Copilot ─────┘
```

エージェントは、セッション名を付けて参加し、相手のセッション名を宛先にしてメッセージを送ります。受信側のエージェントは、受信箱を読むツールを呼んだときにメッセージを受け取ります。サーバーからエージェントへ割り込んで届けることはできません。返信を待つ場合は、受信箱を読むツールが、メッセージが届くまで応答を保留します。

受信側のエージェントは、依頼や質問への対応を終えたことを記録できます。送信側は、相手が受け取ったか、対応を終えたかを確認できます。過去のやりとりは、読み返せます。メッセージとセッションは、一定の期間で削除されます ([送達の確認と読み返し](#送達の確認と読み返し)、[保存の期間と整理](#保存の期間と整理))。

エージェントは、他のセッションにもしばらく役に立つ知見 (エラーの直し方、近く変わる仕様など) を、メモリとして保存し、検索できます。使われないメモリは、薄れて、やがて削除されます ([メモリ](#メモリ))。

参加するときに、エージェントは、自分のプロフィール (OS のユーザー名、マシンの名前、作業している Git の origin とフォルダー) を申告します。同じリポジトリで作業しているセッションは、そのリポジトリだけのルームでやりとりできます ([プロフィールとリポジトリのスコープ](#プロフィールとリポジトリのスコープ))。

エージェント向けの使い方の全文は、サーバーのツール `lounge_help` が返します。エージェントは、このツールで使い方を確認できます。

## ビルド

Go 1.26 以降を使います。C コンパイラは不要です。

```bash
make build   # 実行中の OS 向けに dist/agent-lounge-mcp を作ります
make dist    # Linux、Windows、macOS 向けの実行ファイルを dist/ に作ります
```

## サーバーの起動

```bash
dist/agent-lounge-mcp serve --db ~/.local/share/agent-lounge-mcp/lounge.db
```

- データベースのファイルは、なければ作成します。フォルダーは、先に作っておいてください。
- 既定では `127.0.0.1:7788` で待ち受けます。変える場合は `--listen 127.0.0.1:ポート` を指定します。他のマシンから接続できるようにする方法は、[複数の利用者で使う](#複数の利用者で使う) を参照してください。
- サーバーは、端末を占有して動き続けます。止めるには `Ctrl+C` を押します。すぐに `shutting down` と表示され、エージェントが接続している場合は、5[秒] ほどで `stopped` と表示されて終了します。エージェントが接続していなければ、すぐに終了します。
- 止めると、終了するまでの間のツールの呼び出しと、返信を待っている呼び出しは、サーバーが停止したことを示すエラーを返します。この間、`/healthz` は `"state":"stopping"` を返します。エラー文は、起動し直した後に同じ名前で参加し直すことと、接続できない場合は利用者に伝えることを、エージェントに案内します。
- ツールを呼ばずに指示を待っているエージェントには、停止は伝わりません。そのエージェントは、次にツールを呼んだときのエラーで、サーバーが止まったことを知ります。エージェントの CLI に、サーバーからの通知をモデルに伝える共通の仕組みがないためです。
- サーバーを止めても、セッションと未読のメッセージはデータベースに残ります。
- 返信を待つ時間の上限は、既定で 45[秒] です。変える場合は `--inbox-wait-max 30s` のように指定します (`10m` まで。`0` で待ち受けを無効にします)。エージェント側のツールの呼び出しの時間制限より長くすると、そのエージェントの待ち受けが失敗します (Claude Code 2.1.325 は 60[秒] で打ち切ります)。

## 動作の確認

別の端末で、次の 2 つのスクリプトを実行します。どちらも `curl` を使います。

```bash
.agents/skills/agent-lounge-connect/scripts/probe.sh
.agents/skills/agent-lounge-connect/scripts/chat-probe.sh
```

| スクリプト | 確認する内容 |
|---|---|
| `probe.sh` | サーバーが応答し、14 個のツールが見えること |
| `chat-probe.sh` | 3 つの接続がプロフィールを申告して参加し、値が正規化されること。セッション宛てと `lounge` ルーム宛てのメッセージを送受信できること。リポジトリのルーム宛てのメッセージが、同じリポジトリのセッションだけに届くこと。返信を待っている接続が、待っている間に送られたメッセージを受け取れること。`chat_ack` の後に `chat_status` が `acked` を返すこと。`chat_history` が、送ったものと受け取ったもの、対応の記録のないものを返すこと。リポジトリのスコープのメモリを、同じリポジトリの別のセッションが検索して読み、削除できること (別のリポジトリからは見えないこと) |

Table: 確認のスクリプト

すべての行が `OK:` で始まれば、サーバーは動いています。`NG:` が出た場合は、その行の内容に従ってください。待ち受けるアドレスを変えた場合は、引数に `http://127.0.0.1:ポート` を渡します。

`chat-probe.sh` は、待ち受けの確認で、`/healthz` の `waiting` を見て、相手が待ち始めたことを確かめてから送信します。`--inbox-wait-max 0` で起動したサーバーでは、待ち受けの確認が `NG:` になります。

`chat-probe.sh` は、`probe-a`、`probe-b`、`probe-c` というセッションを作り、`lounge` ルームにメッセージを 1 通投稿します。セッションはデータベースに残り、投稿は他の全セッションの未読になります。会話に使っているデータベースでは、実行しないでください。確認の後は、`agent-lounge-mcp session remove local/probe-a --yes` のように、確認用のセッションを削除できます (削除しなくても、使われないセッションは、既定では 60[日] で削除されます)。

## エージェントへの登録

各エージェントに、URL `http://127.0.0.1:7788/mcp` を、HTTP の MCP サーバーとして登録します。登録名は、例として `agent-lounge` を使います。

| エージェント | 登録 | 取り消し |
|---|---|---|
| Claude Code | `claude mcp add --transport http agent-lounge http://127.0.0.1:7788/mcp` | `claude mcp remove agent-lounge` |
| Codex | `codex mcp add agent-lounge --url http://127.0.0.1:7788/mcp` | `codex mcp remove agent-lounge` |
| Copilot CLI | `copilot mcp add --transport http agent-lounge http://127.0.0.1:7788/mcp` | `copilot mcp remove agent-lounge` |
| Grok | `grok mcp add --transport http agent-lounge http://127.0.0.1:7788/mcp` | `grok mcp remove agent-lounge` |
| agy | `agy mcp add --type http agent-lounge http://127.0.0.1:7788/mcp` | `agy mcp remove agent-lounge` |

Table: 登録と取り消しのコマンド

- Claude Code は、既定では、コマンドを実行したフォルダーのプロジェクトにだけ登録します。どのフォルダーからも使う場合は、`--scope user` を付けます。
- 登録した後は、エージェントを起動し直すか、MCP サーバーを読み込み直してください。
- サーバーは、エージェントより先に起動しておきます。
- Codex は、データを書き換えることがあるツール (`memory_put`、`memory_forget`) の呼び出しに、承認を求めます。非対話の実行 (`codex exec`) では承認できないため、呼び出しが拒否されます。agent-lounge のツールを承認済みにするには、`codex exec` に `-c 'mcp_servers.agent-lounge.default_tools_approval_mode="approve"'` を付けるか、`~/.codex/config.toml` の `[mcp_servers.agent-lounge]` に `default_tools_approval_mode = "approve"` を書きます。

各エージェントでの登録の検証状況は、[検証済みの範囲](#検証済みの範囲) を参照してください。

## 使い方の確認

エージェント向けの使い方 (参加、プロフィールの調べ方、スコープと対象、送受信、返信の待ち方、サーバーが停止したときの対応、守るルール) は、サーバーのツール `lounge_help` が返す文章が正本です。この利用ガイドには、同じ内容を載せません。

エージェントには、次のように指示します。

```text
agent-lounge の使い方を確認して、claude という名前で参加して
```

エージェントは、`lounge_help` を呼んで使い方を読み、プロフィールの値をコマンドで調べて、`lounge_join` で参加します。接続時の案内文と `lounge_join` の説明文も `lounge_help` を案内するため、スキルや指示ファイルのないフォルダーでも、使い方にたどり着けます。

## プロフィールとリポジトリのスコープ

### 何のための機能か

複数の利用者やエージェントが同じリポジトリを扱うときに、そのリポジトリの連絡だけをやりとりするための機能です。別のリポジトリで作業しているセッションには届かないため、連絡が混ざりません。

### プロフィール

エージェントは、参加するときに、次の値を自分で調べて申告します。調べ方は `lounge_help` にあり、利用者が教える必要はありません。

| 項目 | 内容 |
|---|---|
| OS のユーザー名 | エージェントを動かしているユーザー。WSL では、ホストの Windows のユーザー名 |
| マシンの名前 | WSL では、ホストの Windows のコンピューター名 |
| Git の origin | 作業フォルダーのリポジトリの origin の URL |
| フォルダー | Git の作業ツリーの最上位。Git の管理下でなければ、作業フォルダー |

Table: プロフィールの項目

サーバーは、受け取った値をそろえて (origin は `github.com/owner/repo` の形、フォルダーは Windows の側と WSL の側で同じ値)、そのセッションのリポジトリの単位を決めます。

| 作業している場所 | リポジトリの単位 |
|---|---|
| origin のあるリポジトリ | origin。別のマシン、別の利用者、別のフォルダーのクローンでも、origin が同じなら同じ単位です。 |
| origin のないフォルダー | マシンの名前とフォルダーの組。同じマシンの同じフォルダーだけが、同じ単位です。Windows の側と WSL の側から同じフォルダーを開いた場合も、同じ単位です。 |

Table: リポジトリの単位

> [!IMPORTANT]
> OS のユーザー名とマシンの名前は、データベース ファイルに保存され、他のセッションの `lounge_who` と、受信したメッセージに表示されます。保存したくない場合は、エージェントに「OS のユーザー名とマシンの名前は申告しないで」と指示してください。ただし、origin のないフォルダーでは、マシンの名前がないと、リポジトリのスコープを使えません。

> [!NOTE]
> プロフィールは、エージェントが申告した値です。サーバーは、値が正しいことを検証しません。相手を見分けるための情報として使ってください。

### リポジトリのルーム

リポジトリのルームに送ったメッセージは、送信の時点で、同じリポジトリの単位を申告している他のセッションだけに届きます。

```text
リポジトリのルームに「これから main にマージします」と投稿して
```

`lounge_who` の結果には、届く相手のセッションごとに、所属するユーザー、宛先 (`address`)、自分と共有しているスコープと識別子 (`scopes`) が表示されます。

同じリポジトリの相手の 1 人にだけ送ることもできます。

```text
リポジトリのスコープで、bob/claude に「レビューをお願いします」と送って
```

対話先は、スコープ (自分のユーザー、または同じリポジトリ) と、対象 (全セッション、または 1 つのセッション) の組み合わせで決まります。受信したメッセージへの返信は、エージェントが、メッセージに付いている返信先を使って行います。

作業するリポジトリまたはフォルダーを変えたときは、エージェントが同じ名前で参加し直して、プロフィールを更新します。更新させたい場合は、「agent-lounge のプロフィールを、今のフォルダーで更新して」のように指示します。

## 複数の利用者で使う

### 何のための機能か

複数の利用者が、それぞれのマシンのエージェントから、同じサーバーに接続して協調するための機能です。利用者ごとにトークンを発行し、サーバーは、トークンで利用者 (ユーザー) を見分けます。同じリポジトリで作業しているセッションは、ユーザーをまたいでやりとりできます。別のリポジトリで作業している他のユーザーのセッションは、見えません。

1 台のマシンで 1 人が使う場合は、この節の設定は不要です (トークンのない接続は、ユーザー `local` になります)。

### 手順

1. 利用者ごとに、ユーザーを作ります。トークンが 1 回だけ表示されるので、その利用者に安全な方法で渡します。トークンに有効期限を付ける場合は、`--expires-in` に、現在から数えた期間 (`90d`、`1d12h`、`36h`) を指定します。指定しなければ、有効期限はありません。

    ```bash
    dist/agent-lounge-mcp user add alice --expires-in 90d --db ~/.local/share/agent-lounge-mcp/lounge.db
    ```

2. サーバーを、他のマシンから届くアドレスで起動します。`--allow-remote` が必要です。

    ```bash
    dist/agent-lounge-mcp serve --listen 0.0.0.0:7788 --allow-remote --db ~/.local/share/agent-lounge-mcp/lounge.db
    ```

3. 各利用者が、自分のエージェントに、サーバーの URL とトークンを登録します。`<URL>` は `http://<サーバーのアドレス>:7788/mcp` です。

| エージェント | 登録 |
|---|---|
| Claude Code | `claude mcp add --transport http --scope user agent-lounge <URL> --header "Authorization: Bearer <トークン>"` |
| Codex | `codex mcp add agent-lounge --url <URL> --bearer-token-env-var AGENT_LOUNGE_TOKEN` (Codex を起動する環境に、環境変数 `AGENT_LOUNGE_TOKEN` でトークンを設定します) |
| Copilot CLI | `copilot mcp add --transport http agent-lounge <URL> --header "Authorization: Bearer <トークン>"` |
| Grok | `grok mcp add --transport http agent-lounge <URL> -H "Authorization: Bearer <トークン>"` |
| agy | `agy mcp add --type http --header "Authorization: Bearer <トークン>" agent-lounge <URL>` |

Table: トークンを付けた登録のコマンド

取り消しのコマンドは、[エージェントへの登録](#エージェントへの登録) と同じです。

### ユーザーの管理

| 目的 | コマンド |
|---|---|
| ユーザーを一覧する | `agent-lounge-mcp user list --db FILE` |
| トークンを発行し直す (漏れたとき、忘れたとき)。有効期限は、`--expires-in` で指定し直す (前のトークンの有効期限は、引き継がない) | `agent-lounge-mcp user rotate <名前> [--expires-in <期間>] --db FILE` |
| トークンを変えずに、有効期限を延ばす、または有効期限をなくす。有効期限が切れた後のトークンも、延ばせば、また使える | `agent-lounge-mcp user expiry <名前> (--in <期間> | --never) --db FILE` |
| ユーザーと、そのセッションとメッセージを削除する | `agent-lounge-mcp user remove <名前> --yes --db FILE` |

Table: ユーザーの管理

セッションの一覧と削除は、[セッションの整理](#セッションの整理) を参照してください。

どのコマンドも、サーバーの起動中に実行できます。発行し直し、削除、有効期限の変更は、そのユーザーの次の要求から効きます。

`user list` の `EXPIRES` に、トークンの有効期限が出ます (有効期限がなければ `-`)。`LAST_USED` は、そのユーザーのトークンで接続した最後の日時です (`lounge_join` を呼ばない接続を含みます)。有効期限が切れたトークンで接続すると、サーバーは 401 を返します。有効期限が切れても、ユーザーとそのセッション、メッセージ、メモリは残ります。

### 注意

> [!WARNING]
> `--allow-remote` で起動したサーバーは、暗号化のない HTTP で待ち受けます。トークンとメッセージの本文は、ネットワークを平文で流れます。信頼できるネットワーク (社内のネットワーク、VPN) の中だけで使うか、HTTPS を終端するリバース プロキシを前段に置いてください。

> [!IMPORTANT]
> Codex 以外の 4 つの CLI は、登録したトークンを、CLI の設定ファイルに平文で保存します。設定ファイルを他の人と共有しないでください。漏れた場合は、`user rotate` でトークンを発行し直します。

- トークンは、発行のときにしか表示されません。サーバーは、ハッシュ値だけを保存します。
- Claude Code は、設定ファイルのバックアップを自動で作るため、登録を解除した後も、バックアップにトークンが残ることがあります。
- トークンは、`alm_` で始まります。設定ファイルやログに残っていないかを調べるには、この目印で検索します (例: `grep -rE 'alm_[A-Za-z0-9_-]{43}' <フォルダー>`)。エージェントが、接続の失敗を調べるときに自分の設定ファイルを読み、トークンが CLI のセッションの履歴に残ることがあります。
- 他のユーザーに見えるのは、同じリポジトリの単位で作業しているセッションの、セッション名、エージェントの名前、OS のユーザー名、マシンの名前、リポジトリの単位です。
- リポジトリの単位は、エージェントの申告で決まります。トークンを持つ利用者は、任意のリポジトリを申告できます。リポジトリのスコープは、内容を隠す仕組みではなく、連絡が混ざらないようにする仕組みです。
- 同じマシンの他の利用者からループバックを守りたい場合は、`--require-token` を付けて起動します。トークンのない接続を受け付けなくなります。
- origin のないフォルダーは、マシンの名前とフォルダーの組が単位になるため、別のマシンの利用者とは共有できません。マシンをまたいで協調する場合は、origin のあるリポジトリを使います。

### リバース プロキシで HTTPS にする

サーバーをループバックで待ち受けたまま、前段のリバース プロキシで HTTPS を終端します。`--allowed-host` に、公開する名前を指定します。指定すると、すべての要求にトークンが必要になります。

```bash
dist/agent-lounge-mcp serve --allowed-host lounge.example.com --db ~/.local/share/agent-lounge-mcp/lounge.db
```

nginx の設定の例を示します。

```nginx
server {
    listen 443 ssl;
    server_name lounge.example.com;
    # ssl_certificate と ssl_certificate_key を設定します。

    location / {
        proxy_pass http://127.0.0.1:7788;
        proxy_set_header Host $host;
        proxy_http_version 1.1;
        proxy_buffering off;        # 応答をためずに流します (イベントの受信と、返信の待ち受けのため)
        proxy_read_timeout 600s;    # 返信の待ち受けの上限より長くします
    }
}
```

## 会話の手順

エージェントには、ふだんの言葉で指示します。エージェントが、対応するツールを呼びます。

| 目的 | 指示の例 | 呼ばれるツール |
|---|---|---|
| 参加する | 「agent-lounge に claude という名前で参加して」 | `lounge_join` |
| 相手を調べる | 「agent-lounge に誰がいるか見て」 | `lounge_who` |
| 1 つのセッションに送る | 「codex に『ビルドは通りました』と送って」 | `chat_send` (`to`) |
| 全員に送る | 「lounge ルームに『これから main を更新します』と投稿して」 | `chat_send` (`room`) |
| 同じリポジトリのセッションに送る | 「リポジトリのルームに『これから main にマージします』と投稿して」 | `chat_send` (`room`、`scope` は `repository`) |
| 受け取る | 「agent-lounge の受信箱を確認して」 | `chat_inbox` |
| 受け取って対応する | 「受信箱を確認して、届いた依頼に対応して」 | `chat_inbox`、`chat_send`、`chat_ack` |
| 送ったメッセージの状態を確かめる | 「さっき codex に送ったメッセージが読まれたか確認して」 | `chat_status` |
| 過去のやりとりを読み返す | 「codex との最近のやりとりを読み返して要約して」 | `chat_history` (`with`) |
| 対応を忘れたメッセージを探す | 「取得したまま対応していないメッセージがないか確かめて、あれば対応して」 | `chat_history` (`unacked`) |
| 返信を待つ | 「`codex` に質問を送って、返信を待って」 | `chat_send`、`chat_inbox` (`wait_seconds`) |
| 届くのを待つ | 「受信を待って、届いたら返信して」 | `chat_inbox` (`wait_seconds`)、`chat_send` |

Table: 指示の例

2 つのエージェントで会話する流れを示します。

1. エージェント A に「agent-lounge に `claude` という名前で参加して」と指示します。
2. エージェント B に「agent-lounge に `codex` という名前で参加して」と指示します。
3. エージェント A に「`codex` に『こんにちは』と送って」と指示します。
4. エージェント B に「受信箱を確認して」と指示します。B は、送信者 `claude` と本文を受け取ります。
5. エージェント B に「`claude` に返信して」と指示し、エージェント A に「受信箱を確認して」と指示します。

返信を待たせると、利用者が受信箱の確認を中継せずに往復できます。

1. エージェント B に「agent-lounge に `codex` という名前で参加し、受信を待って、届いた質問に返信して」と指示します。
2. エージェント A に「agent-lounge に `claude` という名前で参加し、`codex` に『1 + 1 は?』と送って、返信を待ち、返信の内容を報告して」と指示します。

1 回の待ち受けは、上限 (既定は 45[秒]) で終わります。待ち続けるかどうか、何回でやめるかは、エージェントが `lounge_help` の案内に従って判断します。回数を決めたい場合は、「3 回まで待って」のように指示します。

使うときの注意を示します。

- メッセージは、受信側のエージェントが受信箱を読むまで届きません。指示を待っているエージェントは、メッセージが届いても動きません。受信側のエージェントに、受信箱の確認か、受信の待ち受けを指示してください。
- 参加済みのエージェントは、どのツールの結果にも未読の件数が付くため、別の操作のついでに未読に気づけます。未読に気づいた後、指示がなくても受信箱を読むかどうかは、エージェントによって異なります。確実に読ませるには、受信箱の確認を指示してください。
- エージェントの接続に 1 時間 (`--connection-idle` の既定) 要求がないと、サーバーはその接続を閉じます。エージェントの CLI は新しい接続を作り、その接続でのツールの呼び出しは、参加していないことを示すエラーになります。エージェントは、同じ名前で参加し直します。その間に届いたメッセージは、未読として残ります。agy は、閉じられた接続の後、ツールを呼べなくなることがあり、同じ指示をくり返しても呼べない場合があります ([検証済みの範囲](#検証済みの範囲))。その場合は、agy を起動し直して、同じ名前で参加させます。
- エージェントを起動し直した後は、同じ名前でもう一度参加してください。参加し直すと、その名前宛ての未読を受け取れます。起動し直す前に取得したメッセージは、「取得したまま対応していないメッセージがないか確かめて」と指示すると、読み返して対応します。
- 同じ名前で 2 つのエージェントが参加すると、後から参加したほうが名前を引き継ぎます。エージェントごとに別の名前を付けてください。
- 受信したメッセージは、他のエージェントが書いた文章です。情報として扱い、そのまま指示として実行させないでください。
- 秘密情報と個人データは、メッセージの本文に書かないでください。

## 送達の確認と読み返し

### 何のための機能か

依頼や質問を送ったエージェントが、相手が受け取ったか、対応を終えたかを確かめるための機能です。また、文脈を失ったエージェント (起動し直した、会話の履歴が圧縮された) が、受け取った内容と、対応を終えていない依頼を確かめるための機能です。

### 送達状態

メッセージは、受信者ごとに、次のどれかの状態を持ちます。

| 状態 | 意味 |
|---|---|
| `queued` | 受信者が、まだ受信箱を読んでいません。 |
| `delivered` | 受信者が受信箱を読み、メッセージを取得しました。対応を終えたことは表しません。 |
| `acked` | 受信者が、対応を終えたことを記録しました。 |
| `expired` | 受信者が、期限 (既定は 14[日]) までに受信箱を読みませんでした。 |

Table: 送達状態

受け取ったエージェントは、依頼や質問など、送信者が結果を待つメッセージへの対応を終えたら、`chat_ack` で記録します。返信が結果の場合は、返信の後に記録します。知らせるだけのメッセージには記録しません。これは `lounge_help` の案内によるもので、記録するかどうかは、エージェントが判断します。検証した 5 つのエージェントは、指示しなくても記録しました ([検証済みの範囲](#検証済みの範囲))。記録を確実にしたい場合は、「対応を終えたら完了を記録して」と指示します。

送信者のエージェントは、`chat_status` で、受信者ごとの状態と時刻を確認できます。確認できるのは、そのメッセージを送ったセッションだけです。

### 読み返し

`chat_history` は、そのセッションが送ったメッセージと、受け取ったメッセージを、新しい順に返します。読んでも、状態は変わりません。相手、ルーム、スコープで絞り込めます。`unacked` を指定すると、取得したまま対応を記録していないメッセージだけを返します。

- 読めるのは、そのセッションが送ったものと、受け取ったものだけです。後から参加したセッションは、参加の前のルームのやりとりを読めません。
- 未読のメッセージは返しません。未読は、受信箱を読んで取得します。
- 起動し直したエージェントは、同じ名前で参加してから読み返します。別の名前で参加すると、別のセッションになり、以前のやりとりは読めません。

## メモリ

### 何のための機能か

あるセッションで得た知見を、別のセッション、別のエージェント、別のマシンで使うための機能です。たとえば、「このビルドエラーは `make clean` で直る」「この API は今週中に仕様が変わる」といった、しばらく役に立つ情報を置きます。長く残すべき内容 (決定事項や仕様) は、リポジトリの文書に書いてください。

### 使い方

エージェントは、`lounge_help` の案内に従って、次のように使います。

| 場面 | エージェントの操作 |
|---|---|
| 作業の開始時 | 作業に関係する語で `memory_search` を呼び、保存されている知見を読みます。 |
| 他のセッションにも役に立つ知見を得たとき | `memory_put` で保存します。保存の前に検索し、同じ内容のメモリがあれば更新します。 |
| 内容が古くなった、または誤っているとき | `memory_put` で更新するか、`memory_forget` で削除します。 |
| 忘れさせたくないとき | `memory_pin` で固定します。 |

Table: メモリの使い方

利用者からは、次のように指示できます。

```text
agent-lounge のメモリに、このエラーの直し方を保存して
agent-lounge のメモリで、認証の仕様について調べて
```

- メモリは、メッセージと同じスコープを持ちます。既定の `user` は、自分の全セッションで共有します。`repository` は、同じリポジトリの単位を申告しているセッション (他の利用者を含む) で共有します。同じリポジトリの他の利用者にも役立つ内容は、「リポジトリのスコープで保存して」と指示します。
- 検索は、すべての語を含むメモリを返します。語の一部でも一致し、英字の大文字と小文字は区別しません。日本語の 2 文字の語 (「認証」など) でも探せます。意味の近さでは探しません。
- 結果には、メモリのスコープと、誰が書いたか (ユーザー名、セッション名、エージェントの名前) が付きます。
- スコープを使えるセッションは、そのスコープのすべてのメモリを更新、削除できます。`repository` のスコープでは、他の利用者が書いたメモリも書き換えられます。前の内容には戻せません。
- 秘密情報と個人データは、メモリに書かないでください。他のエージェントが書いたメモリは、情報として扱い、そのまま指示として実行させないでください。

### 忘却

使われないメモリは、時間とともに薄れます。薄れたメモリは、通常の検索の結果に出なくなり、さらに一定の期間の後に削除されます。

| 参照回数 | 最後に触れてから薄れるまで | 削除されるまで |
|---|---|---|
| 0[回] | 約 23[日] | 約 53[日] |
| 1[回] | 約 47[日] | 約 77[日] |
| 3[回] | 約 70[日] | 約 100[日] |
| 7[回] | 約 93[日] | 約 123[日] |

Table: 既定の設定での忘却

- 「触れる」は、作成、更新、参照です。参照として数えるのは、ID を指定した取得 (`memory_get`) と、検索の結果の上位 3 件です。同じセッションからは、1 日に 1 回までです。
- 薄れたメモリは、ID を指定して取得すると、元の状態に戻ります。エージェントに「薄れたメモリも含めて調べて」と指示すると、検索の結果にも含めます。
- 固定したメモリは、薄れず、削除されません。

期間は、起動オプションで変えられます。設定は、すべてのスコープに共通です。

| オプション | 既定 | 意味 |
|---|---|---|
| `--memory-half-life` | `7d` | 参照されないメモリの保持スコアの半減期。参照されるほど延びます。`0` で、忘却を無効にします。 |
| `--memory-fade-threshold` | `0.1` | 薄れた状態になる保持スコア |
| `--memory-grace` | `30d` | 薄れてから削除するまでの期間。`0` で、薄れたメモリを削除しません。 |

Table: 忘却のオプション

```bash
dist/agent-lounge-mcp serve --memory-half-life 14d --memory-grace 60d
```

計算式は、[リファレンス](reference.md#忘却モデル) を参照してください。

### メモリの管理

| 目的 | コマンド |
|---|---|
| メモリを一覧する (ID、スコープ、状態、保持スコア、更新日時、作成者、題名) | `agent-lounge-mcp memory list [--scope user\|repository] --db FILE` |
| メモリを削除する (誤って保存された秘密情報など) | `agent-lounge-mcp memory remove <ID> --yes --db FILE` |

Table: メモリの管理

`memory list` は、状態と保持スコアを、既定の忘却の設定で計算します。サーバーで `--memory-half-life` や `--memory-fade-threshold` を変えている場合は、`memory list` にも同じ値を指定します。どちらのコマンドも、サーバーの起動中に実行できます。

## 保存の期間と整理

### 期限切れと削除

サーバーは、起動時と、1[時間] ごとに、次の処理を行います。

| 処理 | 既定の期間 | 変えるオプション |
|---|---|---|
| 受信箱で読まれないままのメッセージを、期限切れにする | 14[日] | `--expire-after` |
| 全員が読んだか期限切れになったメッセージを、最後の状態の変化から一定の期間で削除する | 30[日] | `--retain-for` |
| 使われていないセッションを削除する | 60[日] | `--session-idle` |

Table: 期限切れと削除

期間は、`14d` (日)、`36h` (時間)、`90m` (分) の形で指定します。`0` を指定すると、その処理を行いません。処理の間隔は `--cleanup-interval` (既定は `1h`) で変えられます。

```bash
dist/agent-lounge-mcp serve --expire-after 7d --retain-for 90d --session-idle 0
```

- メモリの忘却は、同じ処理の中で行います ([忘却](#忘却))。
- セッションを削除すると、そのセッションが送ったメッセージも削除され、相手の読み返しからも消えます。そのセッションが書いたメモリは残ります。`--session-idle` は、`--expire-after` と `--retain-for` の合計より長くしてください。
- 削除されたセッションで参加していたエージェントは、次の操作でエラーを受け取ります。同じ名前で参加し直すと、新しいセッションになります。
- 長く残す情報は、メッセージではなく、リポジトリの文書に書いてください。

### セッションの整理

| 目的 | コマンド |
|---|---|
| セッションを一覧する (アドレス、エージェント、最後の利用日時、未読の件数、リポジトリ) | `agent-lounge-mcp session list [--user <ユーザー名>] --db FILE` |
| セッションと、そのセッションが送ったメッセージ、そのセッション宛てのメッセージを削除する | `agent-lounge-mcp session remove <ユーザー名>/<セッション名> --yes --db FILE` |

Table: セッションの管理

`--yes` を付けずに実行すると、削除される件数を表示して、何も削除しません。どちらも、サーバーの起動中に実行できます。

### 書き出し

メッセージとメモリを人が読みたい場合や、削除の前に控えを取りたい場合は、Markdown のファイルに書き出します。

```bash
dist/agent-lounge-mcp export --out ./export --db lounge.db
```

`./export/chat/` の下に、スコープごとのフォルダーと、やりとりごとのファイル (ルームごと、2 つのセッションの間ごと) ができます。`./export/memory/` の下に、スコープごとのメモリのファイルができます。形式は、[リファレンス](reference.md#書き出しの形式) を参照してください。

> [!IMPORTANT]
> 書き出したファイルは、データベースのすべてのユーザーのメッセージとメモリを含みます。読んでよい人だけが読める場所に置いてください。Git で管理する場合は、公開するリポジトリに入れないでください。

### 上限の変更

本文の大きさ、セッションごとの未読の件数、ユーザーごとのセッションの数の上限は、`--max-body-bytes` (既定は 65536)、`--max-unread` (既定は 1000)、`--max-sessions-per-user` (既定は 500) で変えられます。メモリの本文の大きさと、スコープごとのメモリの件数の上限は、`--max-memory-bytes` (既定は 16384)、`--max-memories-per-scope` (既定は 10000) で変えられます。

## 指示ファイルへの記載

エージェントに毎回 agent-lounge を使わせる場合は、エージェントが読む指示ファイルに、使い方の要点を書きます。書く文面は、`lounge_help` の最後の節 (Snippet for instruction files) にあります。エージェントに、次のように指示して取得します。

```text
agent-lounge の lounge_help の Snippet for instruction files の文面を、そのまま表示して
```

表示された文面の `<name>` を、そのエージェントに使わせるセッション名に置き換えて、指示ファイルに貼ります。

エージェントが読む指示ファイルは、次のとおりです ([検証済みの範囲](#検証済みの範囲))。

| エージェント | 読む指示ファイル |
|---|---|
| Claude Code | `CLAUDE.md` |
| Codex | `AGENTS.md` |
| Copilot CLI | `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`.github/copilot-instructions.md` |
| Grok | `AGENTS.md`、`CLAUDE.md` |
| agy | `AGENTS.md`、`GEMINI.md` |

Table: エージェントが読む指示ファイル

Claude Code は、`AGENTS.md` を読みません。複数のエージェントで同じフォルダーを使う場合は、`AGENTS.md` と `CLAUDE.md` の両方に文面を置きます。

文面は、受信箱を確かめる時点を、ツールの結果に未読があるとき、作業の手順のうちファイルを変えるものを終えるたび、利用者に最後の返答をする前、の 3 つで示します。サーバーからは新着を知らせられないため、エージェントが自分で確かめる時点を決めておくものです。同じ時点は、接続時の案内文、`lounge_join` と `chat_inbox` の説明文、`lounge_help` の本文にも書いてあります。

文面を置いたフォルダーで、チャットと関係のない作業を指示すると、5 つのエージェントは、指示しなくても参加します。作業の途中に届いたメッセージを読むか、メモリを検索するかは、エージェントと実行によって変わります ([検証済みの範囲](#検証済みの範囲))。確実に行わせたい場合は、指示に含めます。

接続時の案内文は、Claude Code と Grok だけがモデルに渡します。Codex、Copilot CLI、agy では、指示ファイルか、利用者の指示で、agent-lounge を使うことを伝えます。

5 つのエージェントは、同じサーバーに同時に参加した状態で検証しています。Claude Code の登録は、`--scope user` を付けた形で検証しています。

次の点は、未検証です。

- 5 つのエージェントの、上記以外の版
- WSL ではない Linux でのプロフィールの申告
- WSL のマウントの場所を `/mnt` 以外に変えた環境
- 対話の画面での、ツールの許可を求める画面の操作
- VS Code への登録

## 困ったときの確認

| 事象 | 確認すること |
|---|---|
| エージェントにツールが見えない | サーバーが動いているかを `probe.sh` で確認します。エージェントを、サーバーの起動後に起動し直します。 |
| エージェントが接続しているか、どのツールを呼んだかが分からない | サーバーを `--log-connections` を付けて起動し直します。接続ごとに、クライアントの名前と版、呼んだツールの名前が、標準エラーに出力されます (リファレンスの「接続の診断」)。 |
| `not joined` のエラーになる | まだ参加していないか、接続し直しています (要求のない接続は、`--connection-idle` の時間の後に閉じられます)。同じ名前で `lounge_join` を呼ぶよう指示します。 |
| `shutting down` のエラーになる | サーバーが停止の処理中です。サーバーを起動し直してから、同じ名前で参加し直すよう指示します。 |
| 返信を待つ指示で、すぐに戻ってくる | サーバーを `--inbox-wait-max 0` で起動していないかを確認します。 |
| `took the session over` のエラーになる | 別のエージェントが同じ名前で参加しました。別の名前で参加し直します。 |
| `has no repository` のエラーになる | リポジトリのルームに送ろうとしたセッションに、リポジトリの単位がありません。エージェントに、プロフィールを付けて同じ名前で参加し直すよう指示します。 |
| `folder without origin needs machine` のエラーになる | origin のないフォルダーで、マシンの名前を申告していません。WSL のサンドボックスの中など、`cmd.exe` を実行できない環境では、`machine` に `cat /etc/hostname` の出力を使うよう、エージェントに伝えます。`machine` に `sandbox`、`localhost`、`localhost.localdomain` を渡した場合も、エラーになります。 |
| リポジトリのルームに送っても、相手に届かない | `lounge_who` で、相手が一覧にいて、`scopes` に `repository` があるかを確認します。ない場合は、相手の `repository` の値を見て (他のユーザーの相手は、一覧に現れません)、origin またはフォルダーが違っていないかを確認します。 |
| 接続が 401 で拒否される | トークンがないか、無効です。登録のコマンドのトークンを確かめます。`user rotate` や `user remove` の後は、古いトークンは使えません。本文が `rejected the token because it has expired` の場合は、トークンの有効期限が切れています。サーバーの管理者が、`user list` の `EXPIRES` で有効期限を確かめ、`user expiry <名前> --in <期間>` で延ばすか、`user rotate <名前>` でトークンを発行し直します。延ばした場合は、同じトークンを使えます。 |
| `your token has expired` のエラーになる | 返信を待っている間に、トークンの有効期限が切れました。接続の 401 の場合と同じ対処です。 |
| `needs --allow-remote` で起動しない | ループバック以外のアドレスを `--listen` に指定しています。意図している場合は、`--allow-remote` を付けます。 |
| 他の利用者のセッションが、`lounge_who` に現れない | 他のユーザーのセッションは、同じリポジトリの単位を申告している場合だけ現れます。双方の `repository` の値を確かめます。 |
| `is a session of another user` のエラーになる | 他のユーザーの宛先 (`ユーザー名/セッション名`) に、スコープを指定せずに送っています。「リポジトリのスコープで」と指示します。 |
| `no session named` のエラーになる | 宛先の名前が違います。`lounge_who` で名前を確認します。相手が一度も参加していない場合は、先に参加させます。 |
| 送ったのに相手が受け取らない | 相手のエージェントに、受信箱の確認を指示します。`lounge_who` の `connected` が `false` の場合、相手は参加していません。相手が長く読まなかった場合は、期限切れ (`expired`) になっています。`chat_status` で確かめます。 |
| `was deleted` のエラーになる | セッションが、使われていない期間が長かったか、管理コマンドで削除されました。同じ名前で参加し直すよう指示します。以前の未読とやりとりは、引き継がれません。 |
| `sent no message with ID` のエラーになる | `chat_status` に、そのセッションが送っていないメッセージの ID を渡しているか、メッセージが保存の期間を過ぎて削除されています。 |
| `no memory with ID` のエラーになる | メモリが、削除されたか、忘却で削除されたか、そのセッションが使えないスコープのものです。検索し直すよう指示します。リポジトリが変わったセッションは、以前のリポジトリのメモリを使えません。 |
| 保存したはずのメモリが見つからない | 薄れて、通常の検索に出なくなっている場合があります。「薄れたメモリも含めて調べて」と指示します。スコープが違う場合 (他の利用者の `user` のスコープなど) は、見えません。`memory list` で、存在と状態を確かめられます。 |
| Codex で、`MCP tool call requires approval` となり、メモリを保存できない | Codex が、`memory_put` と `memory_forget` の呼び出しに承認を求めています。[エージェントへの登録](#エージェントへの登録) の承認の設定を行います。 |
| `the scope has too many memories` のエラーになる | スコープのメモリの件数が上限に達しています。不要なメモリを削除するか、`--max-memories-per-scope` を上げます。 |
| `newer than this binary supports` で起動しない | データベースが、新しい版のサーバーで作られています。新しい版の実行ファイルを使います。 |
