## BL-004 `shared` の空間と `scope` 引数

- **現状の事象**: `user` の空間だけを実装しています。ツールに `scope` 引数がなく、`shared` の `lounge` ルーム (スキーマの初期データにあります) は使えません。企画提案書は、すべての操作が `scope` を持つことを要件としています。

- **本来あるべき姿**: サーバーが、CLI の使う新しいプロトコルの版に応えます。

### 経緯と見送り理由

- **摘出契機**: 案件 `interactive-verification` の実装中に判明しました (接続の診断の出力)。
- **今回の見送り理由**: 2026-07-28 に対応する Go SDK は先行版 (v1.9.0-pre.1) だけで、対応は状態を持たない受け口に限られます。参加を MCP の接続に結び付けている今の設計 (`internal/tools/presence.go`) を作り直す必要があります。古い版での接続し直しで、5 つの CLI は使えています (検討用 Markdown `261119-connection-guidance-discussion.md` の Q-003)。
- **継続作業での経緯と対処**: 案件 `interactive-verification` で追加しました (2026-11-19)。案件 `connection-guidance` で、元の項目の 2 番 (停止の通知の手段) を対応しました。停止のログ通知とログの機能の宣言をやめ、停止はツールの呼び出しのエラーだけで伝えます (2026-11-20、Q-004、最終仕様の第 2 章)。1 番 (版への対応) は、今の動作をテストで保ち、この項目に残しました (Q-003、最終仕様の第 3 章)。 `261119-connection-guidance-backlog.md` の同じ課題 ID から、案件 `small-fixes` の残課題一覧 (この文書) へ転記しました (2026-11-20)。 `261120-small-fixes-backlog.md` の同じ課題 ID から、案件 `expiry-sandbox-verification` の残課題一覧 (この文書) へ転記しました (2026-11-20)。

### 影響範囲とリスク

- **影響対象**: `internal/server/` (HTTP の受け口)、`internal/tools/presence.go` (参加と接続の結び付け)、`docs/ja/reference.md` (MCP サーバーとしての振る舞い、制限事項)。
- **放置した場合のリスク**: CLI が、古い版での接続し直しをやめると、接続できなくなります。`protocol_test.go` は、SDK を上げたときの動作の変化を検出しますが、CLI の側の変化は検出しません。

### 推奨される対応策

- **恒久対応案**: Go SDK の正式版 (v1.9.0 以降) が出た時点で、状態を持たない受け口での参加の扱い (接続ではなく、要求ごとの識別での結び付け) を設計します。あわせて、各 CLI の版の上がり方 (古い版での接続し直しを続けるか) を、検証の基盤の接続の診断で確かめます。
- **参考情報**: Go SDK v1.9.0-pre.1 の `docs/protocol.md` と `docs/mcpgodebug.md`。`internal/server/server.go` の `Handler` のコメント。

## BL-040 agy が、閉じられた MCP の接続の後に、ツールを呼べなくなる

### 概要と問題点

- **現状の事象**: サーバーが要求のない MCP の接続を閉じた後 (`--connection-idle`、既定は 1 時間。閉じた接続への要求は HTTP の 404)、agy (1.5.12) の対話の画面で指示をすると、agy は新しい接続を作り、初期化とツールの一覧の取得を終えます。しかし、モデルが MCP のツールを呼ぶための道具 (`call_mcp_tool`) が「unknown tool」になり、ツールを呼べません。確認した 5 回で、1 回目の指示は 5 回とも失敗しました。2 回目の指示を送った 2 回では、1 回は参加し直して使え、1 回は再び失敗しました。
- **本来あるべき姿**: 接続し直した後の 1 回目の指示から、ツールを使えます (Claude Code、Codex、Copilot CLI、Grok は、そう動きました)。

### 経緯と見送り理由

- **摘出契機**: 案件 `connection-guidance` の前提調査で判明しました (2026-11-19)。BL-039 の対策の前に、使われない接続を 30 秒で閉じる確認用のサーバーで、5 つの CLI の動作を確かめました (検討用 Markdown `261119-connection-guidance-discussion.md` の Q-016)。
- **今回の見送り理由**: agy の側の不具合と見られ、サーバーの側では直せません。利用者は、使われない接続を閉じる設定を、この制限を文書に書いたうえで採用しました (Q-016、Q-017)。
- **継続作業での経緯と対処**: 案件 `connection-guidance` で追加しました (2026-11-19)。改善の後のサーバー (`--connection-idle 30s`) で確かめ直し、2 回目の指示でも失敗する場合があることが分かりました (2026-11-20)。利用ガイドの会話の手順と検証済みの範囲、スキルの文書に、agy を起動し直して同じ名前で参加させることを書きました。 `261119-connection-guidance-backlog.md` の同じ課題 ID から、案件 `small-fixes` の残課題一覧 (この文書) へ転記しました (2026-11-20)。 `261120-small-fixes-backlog.md` の同じ課題 ID から、案件 `expiry-sandbox-verification` の残課題一覧 (この文書) へ転記しました (2026-11-20)。

### 影響範囲とリスク

- **影響対象**: agy の利用者。1 時間以上ツールを呼ばなかった agy と、サーバーを起動し直した場合 (確かめていません)。
- **放置した場合のリスク**: 長く使わなかった agy が、起動し直すまでツールを呼べず、メッセージを受け取れません。

### 推奨される対応策

- **恒久対応案**: agy の新しい版で、同じ確認を繰り返します (確認の記録の「閉じられた接続の後の動作」の手順)。直らない場合は、agy の開発元に報告することを検討します。サーバーを起動し直した場合と、起動し直した agy が使えることも確かめます。agy の利用者が多い場合は、`--connection-idle` の既定値を長くすることも検討します。
- **参考情報**: 確認の記録 `261119-connection-guidance-validation.md` の「閉じられた接続の後の動作」。Go SDK の `StreamableHTTPOptions.SessionTimeout`。
