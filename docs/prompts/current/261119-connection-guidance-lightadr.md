## LADR-004 停止の通知の手段

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

サーバーは、停止のとき、ツールの呼び出しのエラーと、MCP のログ通知の両方で伝えていました。ログ通知を残すかを決める必要がありました (BL-036 の 2 番)。

### 得られた事実

- SDK は、ログのレベルを設定したクライアントにだけ、ログ通知を送ります。5 つの CLI は、2 つの OS で、どれもレベルを設定しませんでした (前の案件のシナリオ 1)。
- MCP のログの機能は、プロトコルの版 2026-07-28 で非推奨になりました (SEP-2577)。
- 企画提案書の停止の要件は、ツールの呼び出しのエラーで伝えることです。

### 決定

停止のログ通知をやめ、停止はツールの呼び出しのエラーだけで伝えます。ログの機能の宣言 (`logging` の capability)、接続の診断の `shutdown notice` と `log level` の行、使い方の案内と文書のログ通知の記述を除きます。

## LADR-005 使われなくなった接続の扱い

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

クライアントが閉じずに終了した MCP の接続が、サーバーを止めるまで残ります (BL-039)。この案件で扱うかを決める必要がありました。

### 得られた事実

- サーバーは SDK の `SessionTimeout` を設定していません。値が 0 のとき、SDK は使われない接続を閉じません (Go SDK v1.8.0 の `StreamableHTTPOptions`)。
- Claude Code 2.1.328 の非対話の実行が終わった後も接続が残り、サーバーの停止は、停止の待ち時間 (5[秒]) の終わりまで待ちました。
- SDK は、閉じた接続への要求に、HTTP の 404 (`session not found`) を返します。
- 使われない接続を 30 秒で閉じる確認用のサーバー (一時フォルダーで作成) で、Claude Code 2.1.328、Codex 0.169.0、Copilot CLI 1.0.114、Grok 1.0.89 は、閉じられた後の 1 回目の指示で、接続し直し、同じ名前で参加し直して、メッセージを読みました (各 1 回)。agy 1.5.12 は、接続し直しましたが、MCP のツールを呼ぶ道具 (`call_mcp_tool`) が使えず、1 回目の指示に失敗しました (3 回中 3 回)。次の指示では回復しました (1 回中 1 回)。

### 決定

サーバーは、要求のない MCP の接続を、一定の時間の後に閉じます。時間の既定の値は 1 時間で、起動オプション `--connection-idle` で変えられます。`0` を指定すると閉じません。agy が、閉じられた接続の後の 1 回目の指示に失敗することは、文書の制限に書き、残課題 BL-040 に記録します。

## LADR-008 lounge_help の出力

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

Copilot CLI は、`lounge_help` の出力 (約 43KB) を一度に読めず、一時ファイルに保存して分けて読みます (BL-037 の 3 番)。出力の小さくし方を決める必要がありました。

### 得られた事実

- `lounge_help` の結果は、本文の Markdown (約 22KB) と、同じ本文を入れた構造化の出力 (`structuredContent` の `guide`) を持ちます (`internal/tools/help.go`)。
- 本文は 21,950 バイトです。Copilot CLI 1.0.114 は、本文だけを返す確認用のサーバーでも、一時ファイルに保存しました (21.4 KB)。大きさだけを変えたツールの結果では、19,500 バイトを直接読み、20,600 バイトを保存しました。

### 決定

`lounge_help` の構造化の出力から本文を外し、本文だけを返します。本文は 1 つのまま、18,000 バイト以下にします。案内する規則は減らさず、ツールの説明文と重なる記述や言い回しを縮めます。本文の大きさが 18,000 バイトを超えたら失敗するテストを加えます。

## LADR-011 確認する OS と Windows の側の表し方

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

この案件の確認 (検証の基盤のシナリオと CLI の動作の確認) を、どの OS で行い、確認しない OS を文書と記録でどう表すかを決める必要がありました。

### 得られた事実

- この案件の変更は、サーバーが送る文 (案内、説明文、貼る文面) と設定 (ログ通知、接続を閉じる時間) とテストで、OS によって分かれる処理を含みません。
- 前の案件では、シナリオ 1 から 4 の結果は 2 つの OS で同じでした。シナリオ 5 の回数は、どちらの OS でも実行ごとに変わりました。
- `AGENTS.md` は、文書の検証済みの範囲の状態を「検証済 / 未検証」で書くと定めていました。利用ガイドには、OS によって変わる部分を変更していないことを理由に、Windows の側を「未検証」とした行が 2 つありました。

### 決定

この案件の確認は、WSL の側だけで行います。Windows の側は、自動テスト、サーバーの動作、CLI の動作のすべてを `-` (本質的に確認の必要がない) で表し、OS によって変わる部分を変更していないことを理由として添えます。`AGENTS.md` の状態の書き方の規則に `-` (理由を添える) を加え、文書でも使います。利用ガイドの同じ性質の既存の 2 行も `-` に改めます。
