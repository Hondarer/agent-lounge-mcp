### 調査で確認した事実

ユーザーが明示した内容は、次のとおりです (対話での指示)。

- 前の案件の成果物を承認し、`main` にマージしました。次の案件を開始します。
- 次の案件の主題は、「対話画面の検証と通知」(BL-018、BL-019、BL-021) です (選択式の質問への回答)。
- 残課題は、その都度、全量を引き継ぎます (以前の案件での指示)。
- この開発を自律的に進めるために、仮想端末を使った検証の基盤が必要な場合は、作成してよい (案件 `chat-autonomy` での指示。BL-018 に記録)。
- 2 つの OS の双方で、またすべてのエージェントで、確認用のフォルダーの中で、サンドボックスを外すオプションを使ってよい (以前の案件での指示)。
- 確認用のデータベースは、`dist/` に置きません (以前の案件での指摘)。

企画提案書で確認したことは、次のとおりです。

- 要件は、「サーバーは、停止するときに、接続中のエージェントへ停止する旨を通知します」です。メッセージの到着を、待機中のエージェントに知らせることは、要件にありません。

現在の実装で確認したことは、次のとおりです。

- 停止のとき、サーバーは、(1) 以後のツールの呼び出しに停止のエラーを返し、(2) 待ち受け中の `chat_inbox` をすぐに返し、(3) 接続中のすべての MCP のセッションに、レベル `warning` のログ通知を送ります (`internal/server/server.go` の `BeginShutdown`)。
- Go SDK (v1.8.0) は、クライアントがログのレベルを設定した (`logging/setLevel` を呼んだ) 接続にだけ、ログ通知を送ります。ログの機能は、プロトコルの版 2026-07-28 で非推奨です (SEP-2577。非推奨の期間は、少なくとも 12 か月)。
- メッセージの到着のとき、サーバーは、宛先のセッションに何も送りません。宛先が知る手段は、ツールの応答に付く未読の件数と、待ち受け中の `chat_inbox` の返却だけです。
- サーバーは、接続ごとの情報 (クライアントの名前と版、ログのレベルを設定したかどうか) を、診断の出力に書きません。
- 接続時の案内文は、`internal/tools/tools.go` の `Instructions` が返す固定の文面です。指示ファイルに貼る文面は、`lounge_help` が返します (貼り先の例は `AGENTS.md` と `CLAUDE.md`)。
- Go SDK (v1.8.0) には、ツールの追加と削除 (`AddTool`、`RemoveTools`。一覧の変更通知が送られます)、リソースの追加と購読 (`AddResource`、`SubscribeHandler`) の機能があります。

このマシン (Linux x86_64、WSL 2) で確認したことは、次のとおりです。

- 5 つの CLI があります。Claude Code 2.1.326、Codex 0.169.0、Copilot CLI 1.0.113、Grok 1.0.77、agy 1.5.10 です。
- `expect` 5.45.4、`script`、Python 3.12.15 (標準の `pty` モジュール) があります。`tmux`、`screen`、Python の端末エミュレーターのライブラリ (`pyte`) は、ありません。
- Windows の側 (同じマシン。Windows 10.0.26300) にも、5 つの CLI と、Python、PowerShell 7 があります。Go は、ありません。
- WSL の側の仮想端末から、WSL の相互運用の機能で Windows のプログラム (`cmd.exe`) を起動し、キー入力を送って、出力を読み取れます (第 1 ターンの回答の後に、一時フォルダーの試験用のスクリプトで確認。[Q-019](#q-019-windows-の側の基盤の作り方))。

未確認のことは、次のとおりです (この案件の作業で確かめます)。

- 5 つの CLI が、接続のときにログのレベルを設定するかどうか。
