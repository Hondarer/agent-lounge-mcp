### 調査で確認した事実

ユーザーが明示した内容は、次のとおりです (対話での指示)。

- 次の作業の設計に着手します。
- 残課題は、その都度、全量を引き継ぎます (前の案件での指示)。
- 参加時のプロフィールに、ユーザー名を含めます。WSL の場合は、ホストの Windows のユーザー名です (BL-024)。
- 参加時のプロフィールに、Git の origin があれば、そのリポジトリの URL を含めます。作業フォルダーを変えながらの作業を考慮し、エージェントの判断でこの値を更新できる構成にします (BL-025)。
- ルームとメモリの単位に、リポジトリを追加します。origin が同じ複数のセッションの間で有効な単位です (BL-026)。
- origin がない場合は、同じマシンの同じフォルダーを指していれば、同じリポジトリの単位として扱います。Windows と WSL のパスは解決し、同じ実体なら同じとします。

現在の実装で確認したことは、次のとおりです。

- `lounge_join` の引数は、`name` と `agent` の 2 つです。`agent` は、省略すると記録済みの値を保ち、同じ名前で呼び直すと更新できます。
- `sessions` テーブルの列は、`user_id`、`name`、`agent`、作成時刻、最終利用時刻です。
- ルームは `lounge` だけで、参加の記録を持ちません。`lounge` 宛ての送信は、送信の時点で存在する、同じユーザーの全セッション (接続中かどうかを問わない) に届きます。
- `chat_send` の宛先は、`to` (セッション名) または `room` (ルーム名) です。`scope` 引数はありません。`rooms` と `messages` の `scope` の列は、`user` と `shared` だけを許す定義です。
- 認証はなく、すべての接続が固定のユーザー `local` です。サーバーは、ループバックのアドレスだけで待ち受けます。このため、今つながるエージェントは、すべてサーバーと同じマシンで動いています (WSL と、そのホストの Windows を含みます)。
- メモリ機能は、未実装です。

このマシン (WSL 2) で確認したコマンドの結果は、次のとおりです。

| コマンド | 結果 |
| --- | --- |
| `git remote get-url origin` (このリポジトリ) | `https://github.com/<所有者>/agent-lounge-mcp.git` の形 |
| `wslpath -w /home/user/agent-lounge-mcp` | `\\wsl.localhost\<ディストリビューション名>\home\user\agent-lounge-mcp` |
| `wslpath -w /mnt/c/Windows` | `C:\Windows` |
| `cmd.exe /c "echo %USERNAME%"` (`/mnt/c` で実行) | ホストの Windows のユーザー名 |

未確認のことは、次のとおりです。

- 5 つのエージェントが、指示がなくても、`lounge_help` の案内に従って上のコマンドを実行し、結果を申告するかどうか。
- Windows の側で動くエージェントからの接続 (このマシンでは、5 つとも WSL の側で動かしています)。

### Q-008 Windows と WSL のパスの解決

**Status**

解決済み

**Question**

Windows のパスと WSL のパスを、同じ実体なら同じ値にする処理を、どの方法で行いますか。

**Context**

同じフォルダーが、Windows と WSL で別のパスになります。このマシンで確認した対応は、次のとおりです。

| 実体 | WSL から見たパス | Windows から見たパス |
| --- | --- | --- |
| Windows のドライブの中 | `/mnt/c/work/app` | `C:\work\app` |
| WSL のディストリビューションの中 | `/home/user/app` | `\\wsl.localhost\<ディストリビューション名>\home\user\app` |

WSL には、WSL のパスを Windows のパスに変換するコマンド `wslpath -w` があり、上の 2 つの対応を、どちらも正しく返します (このマシンで確認済み)。マウントの場所を `/mnt` 以外に変えている環境でも、正しく変換します。

| 案 | 方法 | 特徴 |
| --- | --- | --- |
| A | Windows のパスを共通の表し方とする。WSL のエージェントは、`wslpath -w` で変換した結果を申告する (方法を `lounge_help` に書く)。サーバーは、表記のゆれ (区切り文字、ドライブ名と全体の大文字小文字、`\\wsl$` と `\\wsl.localhost`、末尾の区切り) だけをそろえる | 変換は、実際の対応を知っている WSL が行う。エージェントのコマンドが 1 つ増える |
| B | エージェントは、見えたままのパスを申告する。WSL のエージェントは、ディストリビューション名 (`$WSL_DISTRO_NAME`) も申告する。サーバーが、`/mnt/<ドライブ>/` と、ディストリビューションの中のパスを、規則で Windows のパスに直す | エージェントの作業が少ない。マウントの場所を変えている環境では、サーバーの規則が合わない |

Windows、WSL 以外 (ネイティブの Linux、macOS) では、どちらの案でも、見えたままのパスを申告します。シンボリック リンクは、エージェントが申告の前に解決します (`git rev-parse --show-toplevel` は、解決済みのパスを返します)。

**Answer**

- [x] B: エージェントは見えたままのパスを申告し、サーバーが規則で変換する。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

回答者: Tetsuo Honda

理由: パスの対応は、その WSL の設定で決まるため、WSL 自身のコマンドに任せるのが正確です。サーバーは、推測による変換を持たずに済みます。エージェントが変換を忘れた場合は、別の単位になりますが、`lounge_join` の結果に保存した値を返すため、利用者とエージェントが気づけます。
