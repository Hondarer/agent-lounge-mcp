## 2. Codex の更新の確認を切る (BL-052)

### 2.1. 変更

- `scripts/interactive/harness/agents.py` の Codex の定義の `interactive` に、`-c`、`check_for_update_on_startup=false` を足します (既存の `-c` の承認の設定と同じ形)。コメントで理由 (起動時の更新の案内に答えると、Codex が確認の途中で自分を更新する) を英語で書きます。
- 指示を 1 回だけ実行する起動 (`one_shot`、`codex exec`) は、変えません (対話の画面ではなく、更新の案内を出さないため)。
- 自己試験に、Codex の定義の `interactive` がこのオプションを含むことの確認を足します。

### 2.2. 確認

- 自己試験 (WSL と Windows)。
- このオプションを付けた Codex が、基盤から起動して指示を受け付ける状態になること (WSL と Windows。シナリオ 1 を 1 回)。設定の項目の名前を誤った場合に、Codex が起動を止めないかを確かめるためです。
- 更新の案内が出ないことは、Codex の新しい版が出た時まで確かめられません。文書の検証済みの範囲に「未検証」と書きます。

### 2.3. 文書

`docs/ja/interactive-verification.md` の、CLI の定義の説明の近くに、Codex は起動時の更新の確認を切って起動することを書き、検証済みの範囲に 2.2 の結果の行を足します。

## 3. Windows の Codex のプロフィールの申告 (BL-051)

### 3.1. 割合の確認

Windows 担当が、Windows の Codex (確認の時点の版) で、前の案件と同じ指示と許可 (`codex exec --skip-git-repo-check -s read-only` と agent-lounge のツールの承認) を 5 回実行します。

- サーバーは、Windows のループバック、トークンなし (`127.0.0.1:7903`)。確認用のデータベースは `%TEMP%\alm-wv` の下。
- フォルダーは、前の案件の `%TEMP%\alm-wv\repo` (origin あり、ブランチ `verify/wv-branch`)。
- 指示: 「agent-lounge のツールを使い、使い方の案内 (lounge_help) に従って、`担当-codex<N>` という名前で参加してください。参加の結果の name、user、repository、branch をそのまま答えてください。」(`<N>` は 1 から 5)
- 記録: 参加の結果の `repository` と `branch`、Codex が `cmd.exe` を使ったか (出力から)。

### 3.2. 案内を足す場合

3.1 の結果は、5 回とも `repository` と `branch` が空でした。ただし、事前の確認で、Codex はどのコマンドも `pwsh.exe -Command` で包んで起動し、`cmd.exe /c` も同じエラーで失敗すると分かったため、`cmd.exe /c` の手順を案内に足すことは行いません (3.3 で原因を調べる)。

### 3.3. 原因の調査

Windows 担当が、次を確かめます。Codex の設定は、起動のオプション (`-c`) と、その実行だけの環境変数で一時的に変えます。設定ファイル (`~/.codex/config.toml`) を書き換える必要がある場合は、書き換える前の内容を保存し、確認の後に元に戻します。

1. Codex がシェルを選ぶ仕組みと、関係する設定の項目を、Codex の手元の資料 (`codex --help`、`codex exec --help`、設定の説明) から調べます。
2. サンドボックスの種類による違い: `-s workspace-write` で同じ指示を 1 回実行します。
3. PowerShell の種類による違い: その実行だけ `PATH` から Microsoft Store 版の `pwsh` (WindowsApps) を外し、Windows PowerShell 5.1 またはインストーラー版の PowerShell 7 が使われる状態で、同じ指示を 1 回実行します。1 で設定の項目が見つかった場合は、それで選びます。
4. 値を取れた構成があれば、その構成で 3.1 と同じ指示を 3 回実行し、`repository` と `branch` が値を持つことを確かめます。
5. 結果を確認の記録に書きます。案内か文書を変える必要が出た場合は、変え方を利用者に確かめてから行います。変えない場合は、利用ガイドの検証済みの範囲と制限に、結果 (失敗する構成と、値を取れた構成) を書きます。

### 3.4. 文書

使い方の案内 (`internal/tools/help.go`) は変えません。`docs/ja/user-guide.md` を次のように変えます。

- プロフィールの節に、注意 (Windows の Codex のサンドボックスは、Microsoft Store 版の PowerShell 7 の実行エイリアスを起動できず、プロフィールが空になる) と回避の手順 (Codex を起動するときの `PATH` から `WindowsApps` を外す。Git for Windows の `usr\bin` より `System32` を先に置く) を書きます。
- 困ったときの確認に、リポジトリの単位やブランチがない Windows の Codex のセッションの行を足します。
- 検証済みの範囲に、3.1 と 3.3 の結果の行を足します。

Codex の開発元への報告の文面と、インストーラー版の PowerShell 7 での確認は、残課題に残します。

## 4. agy の開発元への報告の文面 (BL-040)

- 確認の記録 `261125-backlog-followup-validation.md` に、報告の文面 (英語) を置きます。送るのは利用者で、エージェントは外部へ送りません。
- 文面の内容: 現象 (MCP の Streamable HTTP の接続がサーバーに閉じられた後、またはサーバーの起動し直しの後の 1 回目の指示で、`call_mcp_tool` が `unknown tool` になる)、確かめた版と OS (agy 1.5.12 から 1.5.17、Linux (WSL 2) と Windows 11)、再現の手順 (agent-lounge-mcp を `--connection-idle 30s` で起動し、agy から参加させ、50 秒待ってからツールを使う指示をする)、期待する動作、回数の記録 (1.5.17 で 12 回中 12 回)、agy の側では新しい接続の初期化とツールの一覧の取得が終わっていること (サーバーの記録)。
- 利用者の環境の固有の情報 (ユーザー名、コンピューター名、パス、トークン) は含めません。
- サーバー、文書、`--connection-idle` の既定値は変えません。BL-040 は、報告を送った後も、直るまで残課題に残します。
