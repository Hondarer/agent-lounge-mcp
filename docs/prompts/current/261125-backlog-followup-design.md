## 2. Codex の更新の確認を切る (BL-052)

### 2.1. 変更

- `scripts/interactive/harness/agents.py` の Codex の定義の `interactive` に、`-c`、`check_for_update_on_startup=false` を足します (既存の `-c` の承認の設定と同じ形)。コメントで理由 (起動時の更新の案内に答えると、Codex が確認の途中で自分を更新する) を英語で書きます。
- 指示を 1 回だけ実行する起動 (`one_shot`、`codex exec`) は、変えません (対話の画面ではなく、更新の案内を出さないため)。
- 自己試験に、Codex の定義の `interactive` がこのオプションを含むことの確認を足します。

### 2.2. 確認

- 自己試験 (WSL と Windows)。
- このオプションを付けた Codex が、基盤から起動して指示を受け付ける状態になること (WSL と Windows。シナリオ 1 を 1 回)。設定の項目の名前を誤った場合に、Codex が起動を止めないかを確かめるためです。
- 更新の案内が出ないことは、Codex の新しい版が出た時まで確かめられません。文書の検証済みの範囲に「未検証」と書きます。

### 2.3. 文書

`docs/ja/interactive-verification.md` の、CLI の定義の説明の近くに、Codex は起動時の更新の確認を切って起動することを書き、検証済みの範囲に 2.2 の結果の行を足します。

## 3. Windows の Codex のプロフィールの申告 (BL-051)

### 3.1. 割合の確認

Windows 担当が、Windows の Codex (確認の時点の版) で、前の案件と同じ指示と許可 (`codex exec --skip-git-repo-check -s read-only` と agent-lounge のツールの承認) を 5 回実行します。

- サーバーは、Windows のループバック、トークンなし (`127.0.0.1:7903`)。確認用のデータベースは `%TEMP%\alm-wv` の下。
- フォルダーは、前の案件の `%TEMP%\alm-wv\repo` (origin あり、ブランチ `verify/wv-branch`)。
- 指示: 「agent-lounge のツールを使い、使い方の案内 (lounge_help) に従って、`担当-codex<N>` という名前で参加してください。参加の結果の name、user、repository、branch をそのまま答えてください。」(`<N>` は 1 から 5)
- 記録: 参加の結果の `repository` と `branch`、Codex が `cmd.exe` を使ったか (出力から)。

### 3.2. 案内を足す場合

5 回のうち 1 回でも `repository` か `branch` が空の場合は、次を行います。5 回とも値がそろった場合は、案内を変えず、結果を記録して BL-051 を対応済みにします。

- `internal/tools/help.go` の Profile の節の Windows の手順に、シェルを起動できない場合 (サンドボックスの中) は `cmd.exe /c` で同じ値を調べることを、1 文で足します。
- 使い方の案内の大きさは、上限 `maxGuideBytes` (19,300 バイト) を超えないようにします。今は既定の設定で 19,222 バイトのため、足せるのは約 70 バイトです。文は短くし、収まらない場合は、同じ節の他の文を短くして収めます。上限を変える必要がある場合は、作業を止めて利用者に確かめます (上限は Copilot CLI が一度に読める大きさから決めているため)。
- 自動テスト: 案内の大きさの既存のテスト (`internal/tools/catalog_test.go`、`internal/tools/retention_test.go`) が通ること。足した文が案内に含まれることの確認を足します。
- 実機: Windows の 5 つの CLI (Grok は上限であれば未検証) で、3.1 と同じ指示を 1 回ずつ実行し、`repository` と `branch` が値を持つことを確かめます。Codex は、案内を足した後に 5 回実行し、5 回とも値を持つことを確かめます。
- WSL と Linux の手順は変えないため、WSL の側の CLI での確認は行いません (検証済みの範囲に `-` と理由を書く)。

### 3.3. 文書

`docs/ja/user-guide.md` の検証済みの範囲の、Windows の PowerShell でのブランチの申告の行 (Codex の制限ありの記述) を、結果に合わせて書き換えます。

## 4. agy の開発元への報告の文面 (BL-040)

- 確認の記録 `261125-backlog-followup-validation.md` に、報告の文面 (英語) を置きます。送るのは利用者で、エージェントは外部へ送りません。
- 文面の内容: 現象 (MCP の Streamable HTTP の接続がサーバーに閉じられた後、またはサーバーの起動し直しの後の 1 回目の指示で、`call_mcp_tool` が `unknown tool` になる)、確かめた版と OS (agy 1.5.12 から 1.5.17、Linux (WSL 2) と Windows 11)、再現の手順 (agent-lounge-mcp を `--connection-idle 30s` で起動し、agy から参加させ、50 秒待ってからツールを使う指示をする)、期待する動作、回数の記録 (1.5.17 で 12 回中 12 回)、agy の側では新しい接続の初期化とツールの一覧の取得が終わっていること (サーバーの記録)。
- 利用者の環境の固有の情報 (ユーザー名、コンピューター名、パス、トークン) は含めません。
- サーバー、文書、`--connection-idle` の既定値は変えません。BL-040 は、報告を送った後も、直るまで残課題に残します。

## 5. 作業の進め方

1. 作業ブランチ `fix/backlog-followup` を作り、作業前の記録をコミットします。
2. 2.1 の実装と自己試験 (Sonnet のサブエージェント。Claude Code が点検)。
3. 3.1 の確認 (Windows 担当)。結果によって 3.2 (案内の変更は Sonnet のサブエージェント。Claude Code が点検)。
4. 2.2 と 3.2 の実機の確認 (Windows 担当と WSL の側)。
5. 4 章の文面、文書の更新、確認の記録、残課題の整理。
6. `go vet ./...` (Linux と `GOOS=windows`)、`go test ./...`、基盤の自己試験。push は作業ブランチに行い、`main` へのマージは第 3 ゲートで利用者の指示を受けてから行います。CI は `main` へのマージの後に確かめます。

前の案件の進め方 (Windows の側でのビルド、Windows 担当は報告だけ、今の版を記録、上限は未検証として先へ進む) を使います。

## 6. 作業を止める条件

## 7. 受入条件

1. 基盤の Codex の起動のオプションに更新の確認を切る設定があり、自己試験 (WSL と Windows) が通り、Codex がその設定で起動できること。
2. BL-051 の 5 回の結果が記録され、3.2 の条件に従って案内を足した場合は、自動テストと Windows の実機の確認が通ること。
3. agy の報告の文面が確認の記録にあり、利用者の環境の固有の情報を含まないこと。
4. 文書の検証済みの範囲が、結果どおりであること。
5. `go vet ./...`、`go test ./...` が通り、`main` へのマージの後の CI が 3 つの OS で通ること。
6. 対策しなかった項目が、この案件の残課題一覧にあること。

## 8. 第 2 ゲートで確認を受ける細部

決定から一意に決まらない細部です。

- 更新の確認を切るのは、対話の画面の起動だけです (`codex exec` は変えない)。
- BL-051 の 5 回は、前の案件と同じ指示、許可、フォルダーで行います。案内を足すかの判定は、`repository` か `branch` が空になった回が 1 回でもあるかで行います。
- 案内を足す場合の文は、上限に収まる短い 1 文とします。Windows の 5 つの CLI で確かめ、WSL の側では確かめません。
- agy の報告の文面は英語で書きます。
