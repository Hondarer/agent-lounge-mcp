## LADR-002 情報の共有の方針

決定者: Tetsuo Honda  
最終更新日: 2026-11-24

### 背景と課題

`shared` の空間とルームを加えるにあたり、誰がどの情報を読めるかの考え方を決める必要がありました。これまでは、他のユーザーの情報が見えるのは、同じリポジトリの単位を申告している場合だけでした。

### 得られた事実

- リポジトリの単位とブランチは申告で決まり、トークンを持つ利用者は任意の単位を申告できます。文書は、`repository` と `branch` のスコープを、内容を隠す仕組みではなく、連絡が混ざらないようにする仕組みとしています (`docs/ja/reference.md` の「制限事項」)。
- 接続はトークンで認証します。ループバック以外で待ち受ける場合、すべての接続にトークンが必須です (`docs/ja/reference.md` の「認証」)。

### 決定

- この MCP サーバーが管理する情報 (メッセージ、メモリ) は、共有を目的とし、機密情報を含めない前提とします。
- 接続できるか (トークンによる認証) と、接続した利用者の間で情報を共有する範囲は、別に考えます。接続した利用者の間では、情報を広く共有できるようにします。
- この方針により、申告で使えるスコープが決まること (BL-031 の (6)) を、仕様として容認します。

## LADR-003 `shared` のスコープ

決定者: Tetsuo Honda  
最終更新日: 2026-11-24

### 背景と課題

企画提案書が定める 4 つ目の空間 `shared` (全ユーザーの全セッション) を加えるにあたり、使える条件、相手の一覧への載せ方、メモリへの適用、識別子の表し方を決める必要がありました。

### 得られた事実

- 企画提案書は、`shared` を全ユーザーの全セッションが読み書きできる空間とし、識別子を持たないとしています (「空間の分け方」)。
- `lounge_who` は、呼び出し元が使えるスコープの範囲の和を、最終利用時刻の新しい順に 200 件まで返します (`internal/store/chat.go` の `VisibleSessions`)。
- スコープの種類の一覧 (`store.ScopeKinds()`) は、チャットとメモリ、保持の設定、管理コマンドで共通です。

### 決定

- `shared` は、すべてのユーザー (`local` を含む) が常に使えます。有効にする起動オプションは設けません。
- `lounge_who` は、`shared` を含め、届くすべての相手を返します。引数は足さず、上限 (200 件) も変えません。
- チャットとメモリの両方で `shared` を使えます。
- `shared` を使えるすべてのセッションが、すべての `shared` のメモリを更新・固定・削除できます。ユーザーを削除しても、そのユーザーが作った `shared` のメモリは残します (どちらも `repository` と同じ)。
- `shared` のメモリの件数の上限は `--max-memories-per-scope` です。忘却は共通の既定値を使い、`--memory-shared-...` で上書きできます。
- `shared` の識別子は空文字列とし、出力のフィールドは常に返します。書き出しのフォルダーは `shared` とします。

## LADR-004 ルームの作成と参加

決定者: Tetsuo Honda  
最終更新日: 2026-11-24

### 背景と課題

ルームは各スコープの `lounge` だけで、ルーム宛ては範囲の全セッションの未読になります。話題ごとのルームを作り、参加者だけに届ける形にするにあたり、届く範囲、操作の形、作れるスコープ、`lounge` の扱いを決める必要がありました。

### 得られた事実

- 企画提案書は、ルームの作成と参加の操作を定めていません。ツールを 14 個に抑える方針です。
- `rooms` テーブルは、スコープの種類と識別子ごとにルームを持ち、名前はスコープの中で一意です (`internal/store/schema/0007_branch.sql`)。

### 決定

- 作成したルームへの投稿は、そのルームに参加しているセッションだけに届きます。参加の記録を持ちます。
- ルームの操作は、1 つのツール `chat_room` に、`action` で操作 (作成、参加、退出、一覧) を選ぶ形でまとめます。
- すべてのスコープ (`user`、`repository`、`branch`、`shared`) でルームを作れます。
- 各スコープの `lounge` は、範囲の全セッションが常に参加し、退出できません。
- ルームの名前は、ユーザー名と同じ規則 (RFC 8265 の規則、小文字にそろえる) です。
- 1 つのスコープで作れるルームの数に上限を設けます。既定は 100 個で、起動オプションで変えられます。
- 削除の操作は設けません。参加者とメッセージがなくなったルームを、定期の処理で削除します。`lounge` は削除しません。
- ルームを作成したセッションと、参加していないルームに投稿したセッションは、そのルームに自動で参加します。
- リポジトリやブランチが変わっても、以前のスコープのルームの参加の記録は残します。範囲を出ている間は、そのルームの投稿は届きません。

## LADR-005 参加の前のルームのやりとり

決定者: Tetsuo Honda  
最終更新日: 2026-11-24

### 背景と課題

`chat_history` は、自分のセッションが送受信したものだけを返し、後から参加したセッションは参加の前のルームのやりとりを読めません (BL-033 の (1))。申告だけで読める範囲が広がることを理由に、保留されていました。

### 得られた事実

- ルーム宛てのメッセージは、送信の時点の受信者にだけ送達の記録を作ります (`internal/store/chat.go` の `sendToRoom`)。
- メッセージは、未取得の受信者がいなくなり、最後の状態の変化から `--retain-for` (既定は 30[日]) を過ぎると削除されます (`internal/store/cleanup.go`)。

### 決定

- 後から参加したセッションも、参加の前のルームのやりとりを読めるようにします。
- 読めるのは、呼び出し元が今使えるスコープのルームの、削除されていないすべてのやりとりです。ルームに参加しているかは問いません。
- 他のセッションの間のセッション宛てのやりとりは、読めません。

## LADR-007 確認の方法

決定者: Tetsuo Honda  
最終更新日: 2026-11-24

### 背景と課題

ツールの追加と使い方の案内の変更を、どの方法で確認するかを決める必要がありました。これまでの案件では、自動テストに加えて、WSL の側の 5 つの CLI の非対話の実行で確かめてきました。

### 得られた事実

- この案件の変更は、スコープとルームの規則、スキーマ、ツールで、OS によって変わる部分を含みません。
- macOS は、机上の確認と自動テストだけにすると決まっています (利用者の恒久の決定)。
- 利用者によると、Grok はトークンの上限に達し、Copilot CLI も上限が近い状態です (2026-11-24 の回答の補足)。

### 決定

- 自動テスト (`go vet ./...`、`go test ./...`、CI の 3 つの OS) で確認します。
- 実機の CLI での確認は、Claude Code が代表して、WSL の側で、2 つのユーザーで行います (`shared` の送受信、ルームの作成・参加・投稿・退出、参加の前のやりとりの読み返し、`shared` のメモリ)。
- Codex、Copilot CLI、Grok、agy での確認は未検証とし、残課題一覧に記録して、機会を見て行います。
- Windows の実機と macOS は、OS によって変わる部分がないため `-` とします。
