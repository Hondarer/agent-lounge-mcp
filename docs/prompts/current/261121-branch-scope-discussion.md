### Q-001 ブランチを設ける形

**Status**

解決済み

**Question**

「リポジトリよりも詳細な単位としてブランチを設ける」を、どの形で実現しますか。

**Context**

- **経緯と背景**: 利用者の依頼は「repogitory のさらに詳細単位で、branch を設ける計画を詳細検討して」です。今のサーバーは、対話先とメモリの範囲を、スコープ (種類と識別子の組) で決めます。種類は `user` と `repository` の 2 つです。`repository` の識別子は、リポジトリの単位 (origin があれば正規化した origin、なければマシンの名前とフォルダーの組) です。ブランチの情報は、どこにも持っていません。
- **根拠資料**: [internal/store/scope.go](../../../internal/store/scope.go) は、スコープの種類を 1 つの規則 (識別子の決め方、範囲に入るセッション、ルームの置き場所) として定義しています。種類を足すときは、名前と規則を 1 つ足す形です。[docs/ja/reference.md](../../ja/reference.md) の「スコープと対象」が、今の仕様です。
- **各案の具体例**: 同じリポジトリ `github.com/owner/repo` に 3 つのセッションがいる場合で比べます。s1 は `main`、s2 と s3 は `feature/x` で作業しています。s2 が送るときの届き先は、次のとおりです。

| 案 | 同じブランチの相手 (s3) だけに送る | リポジトリの全員 (s1 と s3) に送る |
| --- | --- | --- |
| A | `scope: "branch"` と `room: "lounge"` で送る | `scope: "repository"` で送る (今と同じ) |
| B | `scope: "repository"` で送る (単位がブランチごとになる) | できない (s1 は別の単位になる) |
| C | まとめては送れない。`lounge_who` でブランチを見て、相手ごとに `to` で送る | `scope: "repository"` で送る (今と同じ) |

- A は、スコープの種類を 3 つ (`user`、`repository`、`branch`) にします。`repository` の動作は変わりません。
- B は、リポジトリの単位の決め方を変えます。今の `repository` のスコープのルームとメモリは、単位が変わるため、引き継がれません。
- C は、プロフィールにブランチを足すだけです。範囲を分ける仕組みは足しません。

[Q-002](#q-002-想定する利用場面) 以降の質問は、A を前提に書いています。B または C を選んだ場合は、以降の質問を作り直します (その場合、以降の質問には回答しなくて構いません)。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) スコープの種類に `branch` を足す。範囲は、同じリポジトリの単位と同じブランチを申告しているセッション (ユーザーを問わない)。`user` と `repository` は変えない
- [ ] B: リポジトリの単位を、ブランチごとに分ける (`repository` のスコープが、ブランチごとの範囲になる)
- [ ] C: ブランチをプロフィールの項目として記録し、`lounge_who` に表示するだけにする (スコープは足さない)
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

回答日時: 2026-11-22 09:46:00 JST (検討用 Markdown の保存の時刻)

**Assessment**

A が選ばれました。スコープの種類に `branch` を足します。範囲は、同じリポジトリの単位と同じブランチを申告しているセッションで、ユーザーを問いません。`user` と `repository` は変えません。[Q-002](#q-002-想定する利用場面) から [Q-013](#q-013-使い方の案内文の大きさ) の前提 (A) は、そのまま成り立ちます。

### Q-003 ブランチのスコープを使える機能

**Status**

解決済み

**Question**

ブランチのスコープを、チャットとメモリのどちらで使えるようにしますか。

**Context**

- **経緯と背景**: 今の `user` と `repository` のスコープは、チャット (`chat_send`、`chat_inbox`、`chat_status`、`chat_history`) とメモリ (`memory_put`、`memory_search` ほか) の両方で使えます。企画提案書は、「どちらの機能も」同じ空間を持つとしています (`docs/agent-lounge-mcp-proposal.md`)。
- **根拠資料**: チャットの送信とメモリの作成は、同じスコープの規則を使っています ([internal/store/scope.go](../../../internal/store/scope.go)、[internal/store/chat.go](../../../internal/store/chat.go) の `Send`、[internal/store/memory.go](../../../internal/store/memory.go) の `CreateMemory`)。種類を 1 つ足すと、何もしなければ両方で使える形になります。
- **判断の影響**: ブランチは、リポジトリよりも短い期間で使われなくなります (マージの後に消すなど)。ブランチのスコープのメモリは、そのブランチを申告しているセッションだけが読めます。ブランチが使われなくなると、そのメモリは誰からも参照されず、忘却で薄れて削除されます (既定の設定では、一度も参照されないメモリは約 23[日] で薄れ、その 30[日] 後に削除されます。`docs/ja/reference.md` の「忘却モデル」)。固定したメモリは、削除されずに残ります。
- **各案の具体例**:

| 案 | `chat_send` の `scope: "branch"` | `memory_put` の `scope: "branch"` |
| --- | --- | --- |
| A | 使える | 使える |
| B | 使える | エラー (「メモリのスコープは `user` または `repository`」と案内する) |
| C | エラー | 使える |

**Answer**

選択方式: 単一選択

- [x] A: (推奨) チャットとメモリの両方で使える
- [ ] B: チャットだけで使える (メモリは `user` と `repository` のまま)
- [ ] C: メモリだけで使える
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

回答者: Tetsuo Honda  
回答日時: 2026-11-22 09:46:00 JST (検討用 Markdown の保存の時刻)

**Assessment**

A が選ばれました。ブランチのスコープは、チャットとメモリの両方で使えます。ブランチが使われなくなった後のメモリは読めなくなるため、マージの後も使う知見は `repository` のスコープかリポジトリの文書に保存するように、使い方の案内と文書に書きます。

**Recommendation**

推奨: A  
理由: 企画提案書と今の実装は、チャットとメモリで同じ空間を使います。B と C は、「このスコープは、この機能では使えない」という例外を、エージェントが覚える必要があります。A の制約は、ブランチが使われなくなった後のメモリが読めなくなることです。マージの後も使う知見は、`repository` のスコープか、リポジトリの文書に保存するように、使い方の案内に書きます。

### Q-004 ブランチの名前の調べ方

**Status**

解決済み

**Question**

エージェントは、申告するブランチの名前を、どのコマンドで調べますか。

**Context**

- **経緯と背景**: プロフィールの値は、エージェントが決まったコマンドを実行し、その出力をそのまま `lounge_join` に渡します。サーバーは、値を接続から取得しません。ブランチも、同じ形で申告させる必要があります。別のマシンのセッションと同じ値になるかどうかは、どの名前を使うかで決まります。
- **根拠資料**: 次の表は、一時フォルダーに作ったリポジトリでの確認の結果です (Git 2.56.0、Linux x86_64 (WSL 2)。リポジトリは変えていません)。`git branch --show-current` は、Git 2.22 以降で使えます (Git のリリース ノートによります。手元の確認は 2.56.0 だけです)。

| 状態 | `git branch --show-current` | `git rev-parse --abbrev-ref HEAD` | `git rev-parse --abbrev-ref @{upstream}` |
| --- | --- | --- | --- |
| ブランチ `Feature/日本語-x` にいる | `Feature/日本語-x` | `Feature/日本語-x` | 追跡先がなければエラー (終了コード 128) |
| 作業ツリー (worktree) の中 | その作業ツリーのブランチ (`wt/topic`) | 同じ | 同じ |
| コミットのないリポジトリ | `main` | (確認していません) | (確認していません) |
| ブランチにいない (detached HEAD) | 空の出力 (終了コード 0) | `HEAD` | エラー (終了コード 128) |
| Git の管理下でない | エラー (終了コード 128) | エラー | エラー |

- **各案の具体例**: ローカルのブランチ `fix` が、リモートの `origin/feature/x` を追跡している場合で比べます。

| 案 | 調べ方 | 申告する値 | 別のクローンのセッションと同じ値になる条件 |
| --- | --- | --- | --- |
| A | `git branch --show-current` | `fix` | ローカルのブランチの名前が同じ |
| B | `git rev-parse --abbrev-ref @{upstream}`。失敗したら `git branch --show-current` | `origin/feature/x` (サーバーが、リモートの名前を除いて `feature/x` にする) | 追跡先のブランチが同じ。追跡先がない (まだ push していない) 間は、A と同じ |

- B は、コマンドが 2 つになり、リモートの名前を除く規則と、push の前後で値が変わる動作が加わります。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) ローカルのブランチの名前 (`git branch --show-current` の出力)
- [ ] B: 追跡先 (upstream) のブランチの名前。なければローカルの名前
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

回答者: Tetsuo Honda  
回答日時: 2026-11-22 09:46:00 JST (検討用 Markdown の保存の時刻)

**Assessment**

A が選ばれました。エージェントは、`git branch --show-current` の出力を、そのまま `lounge_join` の `branch` に渡します。同じリモートのブランチを、クローンごとに別のローカルの名前で扱うと別の範囲になることを、文書の制限事項に書きます。

**Recommendation**

推奨: A  
理由: コマンドが 1 つで、push の前でも値が決まります。ブランチにいないときは空の出力になるため、「値がない」ことをそのまま渡せます。制約は、同じリモートのブランチを、クローンごとに別のローカルの名前で扱うと、別の範囲になることです。この制約は、文書の制限事項に書きます。

### Q-005 ブランチがないセッションの扱い

解決済み

- **各案の具体例**:

| 案 | detached HEAD のセッション | 動作 |
| --- | --- | --- |
| A | ブランチは空 | `scope: "branch"` はエラーになり、ブランチにいるときに `lounge_join` で申告するように案内する。`user` と `repository` は、今のとおり使える |
| B | コミットの ID を、ブランチの代わりに申告する | 同じコミットを取り出しているセッションどうしが、同じ範囲になる。コミットを進めるたびに、範囲が変わる |

選択方式: 単一選択

- [x] A: (推奨) ブランチのスコープを使えない (エラーで案内する)。リポジトリの単位が空のセッションも、同じ
- [ ] B: ブランチにいないときは、コミットの ID を代わりに使う
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

回答者: Tetsuo Honda  
回答日時: 2026-11-22 09:46:00 JST (検討用 Markdown の保存の時刻)

**Assessment**

A が選ばれました。ブランチを申告していないセッションと、リポジトリの単位が空のセッションは、ブランチのスコープを使えません。`scope: "branch"` はエラーになり、ブランチにいるときに `lounge_join` で申告するように案内します。`user` と `repository` のスコープは、今のとおり使えます。

### Q-006 ブランチのスコープの識別子の形

**Status**

解決済み

**Question**

ブランチのスコープの識別子を、どの形にしますか。
