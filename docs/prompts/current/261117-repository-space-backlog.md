## BL-001 送達の確認 (`chat_ack`、`chat_status`)

### 概要と問題点

- **現状の事象**: 送達状態は `queued` と `delivered` までを記録します。`delivered` は、受信側のエージェントが `chat_inbox` で取得したことだけを表します。受信者が内容を処理したことを記録する `chat_ack` と、送信者が状態を確認する `chat_status` がありません。`deliveries` テーブルには `acked_at` の列がありますが、使っていません。
- **本来あるべき姿**: 受信者が `chat_ack` で処理の完了を記録でき、送信者が `chat_status` で、自分が送ったメッセージの受信者ごとの状態 (`queued`、`delivered`、`acked`) を確認できます。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (検討用 Markdown の Q-001。今回は 4 つのツールだけを実装する)。到達点からも `acked` の確認を除いています (Q-010)。
- **今回の見送り理由**: スコープ外。疎通確認には、送信と受信だけで足りるためです。
- **継続作業での経緯と対処**: `261117-chat-connectivity-backlog.md` の同じ課題 ID から転記しました。この案件 (`chat-autonomy`) では対策しません (検討用 Markdown の Q-001)。`261117-chat-autonomy-backlog.md` の同じ課題 ID から、案件 `repository-space` の残課題一覧 (この文書) へ転記しました (2026-11-17)。 この案件 (`repository-space`) では対策しません (検討用 Markdown の Q-001)。

### 影響範囲とリスク

- **影響対象**: `internal/store/chat.go`、`internal/tools/chat.go`、`docs/ja/reference.md`。送信側のエージェントとその利用者。
- **放置した場合のリスク**: 送信者は、相手が読んだか、処理したかを確認できません。作業の依頼に使うと、相手の返信を待つ以外に進み具合を知る手段がありません。

### 推奨される対応策

- **恒久対応案**: `chat_ack` (引数: メッセージ ID の一覧。自分宛ての `delivered` を `acked` にする) と `chat_status` (引数: メッセージ ID。送信者本人だけが参照できる) を追加します。スキーマの変更は不要の見込みです。企画提案書の「チャット機能」の定義に合わせます。
- **参考情報**: Q-001、Q-010。`internal/store/schema/0001_init.sql` の `deliveries`。

- **現状の事象**: サーバーは、停止の操作を受けると、接続がある間、5[秒] まで待ってから終了します。この間に 2 回目の `SIGINT` (Ctrl+C) を受けても、待ち時間は短くなりません。
- **本来あるべき姿**: 停止の処理中に 2 回目のシグナルを受けたら、待たずに終了します。

### 経緯と見送り理由

- **摘出契機**: 前の案件の BL-015 の対処の際に見送り、この案件の最終仕様でも「今回実装しないこと」としました。
- **今回の見送り理由**: スコープ外。5[秒] の待機は、利用者が問題ないと判断しています。
- **継続作業での経緯と対処**: `261117-chat-autonomy-backlog.md` の同じ課題 ID から、案件 `repository-space` の残課題一覧 (この文書) へ転記しました (2026-11-17)。 この案件 (`repository-space`) で対策します (最終仕様 `261117-repository-space-design.md`)。

### 影響範囲とリスク

- **影響対象**: `cmd/agent-lounge-mcp/main.go` の停止の処理、`docs/ja/reference.md`。
- **放置した場合のリスク**: 急いで止めたい利用者が、プロセスを強制終了します。その場合も、データベースは WAL のため壊れませんが、エージェントへの通知は行われません。

### 推奨される対応策

- **恒久対応案**: `signal.NotifyContext` の後、停止の処理の間に 2 回目のシグナルを待ち、受けたら `http.Server.Close` を呼んで終了します。表示に「もう一度 Ctrl+C で、すぐに終了する」と加えます。
- **参考情報**: `docs/prompts/past/261117-chat-connectivity-backlog.md` の BL-015。

### 概要と問題点

- **現状の事象**: 参加時のプロフィールに、作業しているリポジトリの情報がありません。`lounge_who` の結果からは、相手のセッションが、どのリポジトリで作業しているかが分かりません。プロフィールを、参加の後に変える手段は、同じ名前で `lounge_join` を呼び直すこと (`agent` の更新) だけです。
- **本来あるべき姿**: 作業フォルダーの Git に origin があれば、そのリポジトリの URL がプロフィールに含まれます。origin がない場合は、マシンと作業フォルダーの組が、リポジトリを表す値としてプロフィールに含まれます (BL-026 で、同じマシンの同じフォルダーを同じリポジトリの単位として扱うため)。エージェントは、作業フォルダーを変えながら作業するため、自分の判断で、この値を更新または消去できます。

- **摘出契機**: 案件 `chat-autonomy` の成果物の承認 (第 3 ゲート) の提示の後に、利用者が要件として示しました (2026-11-17、対話での指示。「不足ならバックログへ」)。現在の実装と企画提案書を確認し、不足していると判断しました。
- **今回の見送り理由**: この案件の最終仕様に含まれない、新しい要件のためです。企画提案書は、まだ更新していません。
- **継続作業での経緯と対処**: 利用者が、origin がない場合の扱いを追加で示しました (2026-11-17、対話での指示。同じマシンの同じフォルダーを指していれば、同じリポジトリの単位として扱う。Windows と WSL のパスは解決し、同じ実体なら同じとする)。`261117-chat-autonomy-backlog.md` の同じ課題 ID から、案件 `repository-space` の残課題一覧 (この文書) へ転記しました (2026-11-17)。 この案件 (`repository-space`) で対策します (最終仕様 `261117-repository-space-design.md`)。

### 影響範囲とリスク

- **影響対象**: サーバーの仕様 (`lounge_join` の引数、プロフィールを更新する手段、`lounge_who` と `chat_inbox` の出力、`sessions` テーブルの列の追加)、`lounge_help` の文面と指示ファイルに貼る文面、`docs/ja/reference.md`。BL-026 の前提です。
- **放置した場合のリスク**: 同じリポジトリで作業している相手を、探せません。BL-026 (リポジトリの単位) に着手できません。

### 推奨される対応策

- **恒久対応案**: `lounge_join` に、省略できる引数 (名前の案: `repository`) を追加します。更新は、参加の後に呼べる手段 (新しいツール、または同じ名前での `lounge_join` の呼び直し) で行い、空の値で消去できるようにします。値は、エージェントが `git remote get-url origin` で調べて申告します。サーバーは、URL を正規化して保存します (認証情報の部分を取り除く、`git@host:owner/repo.git` と `https://host/owner/repo` を同じものとして扱う、末尾の `.git` と大文字小文字の扱いをそろえる)。origin がない場合は、マシンの識別子とフォルダーのパスを申告します。Windows のパスと WSL のパスは、同じ実体なら同じ値になるように解決します (例: `C:\work\app` と `/mnt/c/work/app`、`\\wsl.localhost\Ubuntu\home\user\app` と `/home/user/app`)。検討の際に、マシンの識別子に何を使うか (ホスト名は、Windows と WSL で異なる設定にできます)、フォルダーとして何を申告するか (Git の作業ツリーの最上位か、作業フォルダーそのものか。Git の管理下にないフォルダーの扱い)、パスの解決をエージェントとサーバーのどちらで行うか (シンボリック リンク、大文字小文字、ドライブ名、WSL のディストリビューション名の扱い)、origin 以外のリモートの扱い、エージェントがいつ更新するかの指針 (`lounge_help` に書く内容)、更新を忘れた場合に古い値が残ることの扱いを決めます。
- **参考情報**: `internal/tools/lounge.go` の `JoinInput`。BL-024、BL-026。

## BL-026 ルームとメモリの単位に、リポジトリ (repository) を追加する

### 概要と問題点

- **現状の事象**: 空間は、自ユーザー (`user`) と全ユーザー (`shared`) の 2 つで、今は `user` だけを実装しています。企画提案書は、空間が 2 つであることを、要件として書いています。リポジトリごとの単位はなく、同じリポジトリで作業しているセッションだけに届くルームや、そのリポジトリだけで有効なメモリを作れません。メモリ機能 (BL-012) と `scope` 引数 (BL-004) は、未実装です。
- **本来あるべき姿**: ルームとメモリの単位に、リポジトリ (`repository`) があります。プロフィールの origin (BL-025) が同じ複数のセッションの間で、有効です。origin がない場合は、同じマシンの同じフォルダーを指しているセッションを、同じリポジトリの単位として扱います。Windows のパスと WSL のパスは解決し、同じ実体なら同じとします。そのリポジトリのルーム宛てのメッセージは、同じ origin を申告しているセッションだけに届き、そのリポジトリのメモリは、同じ origin のセッションだけが読み書きできます。

### 経緯と見送り理由

- **摘出契機**: 案件 `chat-autonomy` の成果物の承認 (第 3 ゲート) の提示の後に、利用者が要件として示しました (2026-11-17、対話での指示。「不足ならバックログへ」)。現在の実装と企画提案書を確認し、不足していると判断しました。
- **今回の見送り理由**: この案件の最終仕様に含まれない、新しい要件のためです。企画提案書は、まだ更新していません。
- **継続作業での経緯と対処**: 利用者が、origin がない場合の扱いを追加で示しました (2026-11-17、対話での指示)。本来あるべき姿と対応策に反映しました。`261117-chat-autonomy-backlog.md` の同じ課題 ID から、案件 `repository-space` の残課題一覧 (この文書) へ転記しました (2026-11-17)。 この案件 (`repository-space`) で対策します (最終仕様 `261117-repository-space-design.md`)。

### 影響範囲とリスク

- **影響対象**: 企画提案書の「空間の分け方」(要件の記述の変更が必要)、スキーマ (`rooms`、`messages`、メモリのテーブルの `scope` の値と、リポジトリの識別子)、すべてのツールの `scope` 引数 (BL-004)、ルームの参加の決め方 (BL-009)、メモリ機能 (BL-012)。
- **放置した場合のリスク**: リポジトリに関する連絡と知見が、関係のないセッションにも届き、関係のあるセッションを選べません。`scope` 引数 (BL-004) とメモリ機能 (BL-012) を先に 2 つの空間で実装すると、後からリポジトリの単位を加えるときに、スキーマとツールの引数をもう一度変えることになります。

### 推奨される対応策

- **恒久対応案**: BL-004、BL-009、BL-012 の検討の前に、この単位を含めて空間を設計し直します。`scope` の値に `repository` を加え、対象は、呼び出し元のセッションが申告しているリポジトリの値 (origin があれば正規化した URL、なければマシンの識別子と解決したフォルダーのパスの組) とします。検討の際に、次の点を決めます。(1) `repository` と、`user`、`shared` の関係 (リポジトリの単位が、ユーザーをまたぐかどうか)。(2) origin を申告していないセッションが `repository` を指定した場合の扱い。(3) セッションが origin を変えたときの、未読と参加の扱い。(4) origin は申告の値のため、他のリポジトリを名乗って読めてしまうことの扱い (認証と権限の範囲)。(5) リポジトリごとの既定のルームの名前。(6) origin のないフォルダーに、後から origin が付いた場合の、それまでのメッセージとメモリの扱い (フォルダーの単位から URL の単位へ引き継ぐかどうか)。(7) 同じリポジトリを、origin のあるクローンと、origin のないコピーで使っている場合は、別の単位になること。
- **参考情報**: 企画提案書の「空間の分け方」。BL-004、BL-009、BL-012、BL-025。
