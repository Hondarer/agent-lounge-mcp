# ブランチのスコープ 最終仕様

ファイル名: `261121-branch-scope-design.md`

## 1. 目的と範囲

### 1.1. 目的

対話先とメモリの範囲に、リポジトリよりも詳細な単位として、ブランチを足します。次の 2 つの利用場面を実現します。

| 利用場面 | 例 |
| --- | --- |
| 同じブランチを、複数のマシンや OS のセッションで扱う | WSL の側のセッションが実装して push し、Windows の側のセッションが同じブランチを取得して確認する。依頼と結果を、そのブランチのルームでやりとりする |
| 同じリポジトリで並行する複数の作業の連絡を、作業ごとに分ける | 作業ツリー (worktree) やクローンごとに、別のブランチで別の作業を進める。ある作業の連絡が、他の作業のセッションの未読にならない |

### 1.2. 範囲

- スコープの種類に `branch` を足します。`user` と `repository` の動作は変えません。
- `branch` のスコープは、チャットとメモリの両方で使えます。
- 引き継いだ残課題 14 件 (BL-004、009、011、013、014、028、030、031、033、034、035、036、040、042) は、この案件では対処しません。

### 1.3. 対象外

- 自分が申告していないブランチの内容 (メモリ、ルームのメッセージ) を読む手段。
- サーバーが、ブランチの切り替えを検出したり、書き込みのたびに今のブランチを照合したりする仕組み。
- 追跡先 (upstream) のブランチの名前の利用、ブランチにいないとき (detached HEAD) のコミットの ID の利用。

## 2. 仕様

### 2.1. スコープの種類 `branch`

| 項目 | 内容 |
| --- | --- |
| 範囲 | 同じリポジトリの単位と、同じブランチを申告しているセッション。ユーザーとマシンを問わない |
| 識別子 | `<リポジトリの単位>:<ブランチ>`。例: `github.com/owner/repo:feature/x`、`host-a:c:\work\app:feature/x` |
| 使える条件 | セッションのリポジトリの単位とブランチが、どちらも空でない |
| 使える機能 | チャット (`chat_send`、`chat_inbox`、`chat_status`、`chat_history`) とメモリ (`memory_put`、`memory_search` ほか) |
| 報告する順 | `user`、`repository`、`branch` |

> [!NOTE]
> サーバーは、識別子を分解せず、等しいかどうかだけを比べます。ブランチの名前は `:` を含まない (2.2 の検査) ため、リポジトリの単位とブランチの組が違えば、識別子も違います。

### 2.2. ブランチの申告

`lounge_join` に、引数 `branch` (省略できる文字列) を足します。エージェントは、Git の作業ツリーの中で `git branch --show-current` を実行し、出力をそのまま渡します。出力が空のとき (ブランチにいない、detached HEAD) は、空の文字列を渡します。Git の管理下でないフォルダーでは、渡さないか、空の文字列を渡します。

サーバーは、値を次の規則でそろえます (`internal/profile` の新しい関数 `Branch`)。

| 順 | 規則 |
| --- | --- |
| 1 | 空でない最後の行を取り、前後の空白を除く (`os_user`、`machine` と同じ) |
| 2 | 小文字にする |
| 3 | 空であれば、「値がない」とする |
| 4 | 255 文字を超える値は、エラーにする |
| 5 | `:`、空白、制御文字、`~`、`^`、`?`、`*`、`[`、`\` のどれかを含む値は、エラーにする。Git がブランチの名前に許さない文字で、コマンドのエラー文や `git branch` の一覧の行 (`* main`) を渡した場合も、ここで検出する |
| 6 | 値が `head` (`git rev-parse --abbrev-ref HEAD` の、ブランチにいないときの出力) の場合は、エラーにする |

4 から 6 のエラーの文は、`git branch --show-current` の出力を渡すこと、出力が空のときは空の値を渡すことを案内します。

記録済みの値の置き換えは、次のとおりです。

| 呼び出しで渡した引数 | ブランチ | 場所 (`origin`、`folder`) |
| --- | --- | --- |
| `branch` だけ | 渡した値に置き換える (空の文字列で消去) | 保つ |
| `origin`、`folder`、`wsl_distro` のどれか (`branch` は省く) | 空にする | 置き換える (今の規則) |
| `origin`、`folder`、`wsl_distro` のどれかと `branch` | 渡した値に置き換える | 置き換える (今の規則) |
| どれも省く | 保つ | 保つ |

> [!NOTE]
> 場所を渡した呼び出しでブランチを空にするのは、別のリポジトリへ移ったときに、前のリポジトリのブランチの名前が残って、移った先の同じ名前のブランチの範囲に入るのを防ぐためです。

ブランチは、他のプロフィールの値と同じ扱いです。申告の値で、サーバーは検証しません。リポジトリの単位が空のセッションでも、申告された値は記録して表示します (スコープは使えません)。

`lounge_join` の出力に、`branch` (記録した値。なければ空) を足します。場所を渡し、`branch` を省いた呼び出しで、リポジトリの単位が空でない場合は、出力の `hint` で、`git branch --show-current` の出力を `branch` に渡して呼び直すことを案内します (今の WSL についての案内と両方が当てはまる場合は、両方を載せます)。

### 2.3. 使えない場合のエラー

リポジトリの単位またはブランチが空のセッションが `scope: "branch"` を指定すると、エラーにします (`internal/store` の新しいエラー `ErrNoBranch`)。ツールのエラーの文は、同じ名前で `lounge_join` を呼び直し、origin とフォルダー (または、フォルダーとマシン) と、`branch` (`git branch --show-current` の出力) を渡すこと、ブランチにいないときはブランチのスコープを使えないことを案内します。`lounge_who` の `scopes` には、使えるスコープだけが載ります。

### 2.4. 今の規則の当てはめ

| 事項 | ブランチのスコープでの扱い |
| --- | --- |
| 書き込みの既定 | `chat_send` と `memory_put` の `scope` を省くと `user` (変えない)。`branch` は、明示したときだけ使う |
| 読む操作の既定 | `chat_history`、`memory_search` の `scope` を省くと、使えるすべてのスコープ (`branch` を含む) を読む。`chat_inbox` の待ち受けは、どのスコープの新着でも戻る |
| ルーム | ブランチのスコープごとに `lounge` が 1 つ。最初の送信の時点で作る |
| 他のユーザーの宛先 | `user/name` の宛先には、`scope` (`repository` または `branch`) の明示が要る。宛先の形からは決めない |
| 受信者が決まる時点 | 送信の時点で範囲にいるセッション。後から範囲に入ったセッションには、それ以前のメッセージは届かない。範囲を出たセッションが受け取り済みのメッセージは、変わらない |
| メモリの操作の権限 | スコープを使えるセッションは、そのスコープのすべてのメモリを読み、更新、固定、削除できる。使えないスコープのメモリは、「ない」と報告する |
| メモリの上限と忘却 | ブランチのスコープ 1 つごとに `--max-memories-per-scope` まで。忘却の設定は、すべてのスコープに共通 |
| 引き継ぎ | ブランチを切り替えても、前のブランチの内容は引き継がない (リポジトリの単位が変わったときと同じ) |

### 2.5. 一覧、管理コマンド、書き出し

- `lounge_who`: 一覧に載るすべてのセッションについて、`branch` を表示します (リポジトリの単位と同じ扱い)。自分の値を、最上位の `branch` にも表示します。`scopes` には、共有している `branch` のスコープが載ります。一覧に載るセッションは、増えません。
- `session list`: 列 `BRANCH` を末尾に足します。
- `memory list --scope`: `branch` を受け付けます。
- 書き出し: ブランチのスコープの内容は、今の規則 (`<種類>-<識別子>`) で、`branch-<識別子>` のフォルダーに出力します。
- ツールの引数と出力の説明文、エラーの文の「`user` または `repository`」は、`branch` を加えた文に改めます。

### 2.6. 使い方の案内 (`lounge_help`)

本文に、次の内容を足します。他の記述は縮めません。

| 節 | 足す内容 |
| --- | --- |
| Quick start | ブランチの相手だけに届けるときは `scope` に `branch` を指定すること |
| Profile | ブランチの調べ方 (`git branch --show-current`、空の出力は空の値)、置き換えの規則 (場所を渡すときは `branch` も渡す、`branch` だけでも渡せる)、ブランチを切り替えたら同じ名前で `lounge_join` を呼び直すこと |
| Scopes and targets | `branch` のスコープの範囲と識別子、使えない条件、対象の表の行 |
| Reading past messages、Memory | `scope` の値に `branch` を加える。マージの後も使う知見は、`repository` のスコープかリポジトリの文書に保存すること |
| Limits | ブランチは引き継がれないこと、ローカルの名前で比べること、大文字と小文字を区別しないこと |
| Snippet for instruction files | ブランチを切り替えたときも `lounge_join` を呼び直すこと |

本文の上限 (`maxGuideBytes`) を、19,300 バイトに上げます。`lounge_join` と `lounge_who` と `lounge_help` の説明文にも、ブランチを加えます。また、Forgetting 節に、使われているスコープは現行の日数であること、半減期より長くアクセスが無いスコープは忘却が遅くなり残る期間はおよそ 3 倍を超えないこと、既定値では静かなスコープの参照 0 回は約 56 日で薄れ約 146 日で削除されることを追記します。

> [!IMPORTANT]
> 上限の理由は、Copilot CLI (1.0.114) が、約 20KB を超えるツールの結果を一時ファイルに保存して分けて読むことです (19,500 バイトは直接読み、20,600 バイトは保存しました)。19,300 バイトでは、参加後に付く未読行 (約 50 バイト) を足しても 19,500 バイト未満に収まります。足した後の本文が 19,300 バイトを超える場合は、作業を止めて、利用者に確認します。

### 2.7. データベース (スキーマの版 7)

新しいスクリプト `internal/store/schema/0007_branch.sql` を足します。公開済みのスクリプトは変えません。

- `sessions` に、列 `branch TEXT NOT NULL DEFAULT ''` (そろえたブランチの名前。なければ空) を足します。
- `rooms`、`messages`、`memories` の `scope` の制約 (CHECK) に `'branch'` を加えます。SQLite は制約を変えられないため、版 2 と同じ手順 (新しいテーブルを作り、ID を保って行を写し、古いテーブルを消して、名前を変える) で作り直します。列、索引、他の制約は、版 6 の時点と同じにします。
- `rooms` の列 `repository` は、`repository` のスコープではリポジトリの単位を、`branch` のスコープではスコープの識別子を持ちます。制約は、「`scope` が `repository` または `branch` であることと、`repository` が空でないことが一致する」に改めます。一意の索引 (`scope`、ユーザー、`repository`、`name`) は、変えません。
- `memories` は `AUTOINCREMENT` で、削除したメモリの ID を再び使わないことを保証しています。作り直しでは、`sqlite_sequence` の値を引き継ぎます (最も大きい ID のメモリが削除済みの場合でも、その ID を再び使わない)。全文検索の索引 (`memories_fts`)、`memory_tags`、`memory_refs` は、メモリの ID を保つため、変えません。
- 既存の行の値は変えません。既存のセッションのブランチは、空です。
- 忘却の進み方の調整 (2.8) のため、`memories` に列 `forgetting_credit INTEGER NOT NULL DEFAULT 0` (ミリ秒) を含め、スコープごとの活動テーブル `memory_scope_activity (scope TEXT NOT NULL CHECK (scope IN ('user', 'shared', 'repository', 'branch')), scope_id TEXT NOT NULL, last_access INTEGER NOT NULL, discount INTEGER NOT NULL DEFAULT 0, PRIMARY KEY (scope, scope_id)) STRICT, WITHOUT ROWID` を作成します。移行時に既存メモリのスコープごとに `last_access = max(max(updated_at, accessed_at))`、`discount = 0` の初期行を投入します。

### 2.8. スコープのアクセス間隔に応じた忘却の進み方 (BL-043)

- **対象**: 忘却が有効 (`--memory-half-life > 0` かつ `0 < --memory-fade-threshold < 1`) で固定されていないメモリ。`user`、`repository`、`branch` の全スコープに適用し、起動オプションは追加しません。
- **計算式** (`W = --memory-half-life`、`q = max(0, now - last_access)`):
  - 空白の忘却時計 `g(q) = q` (`q <= W`)、`W + (q - W) / 3` (`q > W`)。
  - 開いている割引 `open_discount = q - g(q)` (`0` または `(2/3) * (q - W)`)。
  - 有効経過 `effective = max(0, (now - base) - (discount - forgetting_credit) - open_discount)`。
  - 保持スコア `2 ^ (-effective / half_life)`、薄れる条件 `effective >= half_life * log2(1 / threshold)`、削除条件 `effective >= half_life * log2(1 / threshold) + grace`。
  - 既定値 (7 日 / 0.1 / 30 日) で、静かなスコープの参照 0 回は約 56 日 (55.760490 日) で薄れ、約 146 日 (145.760490 日) で削除されます。使われているスコープは現行と同じ (約 23 日 / 約 53 日) です。
- **アクセスとして数える操作**:
  - `memory_put` (作成・更新)、`memory_get`、`memory_search` (対象スコープすべて、件数 0 でも進める)、`memory_pin` (固定・解除)、`memory_forget` は、同一トランザクション内で開いている空白を閉じて (`discount += q - g(q)`、`last_access = T`) 更新します。
  - 基準時刻が `T` に動く操作 (作成、更新、参照として数えた取得・検索、固定の解除) は `forgetting_credit = discount` (閉じた後の値) に更新します。基準時刻が動かないメモリは `forgetting_credit` を変えません。
  - 定期削除 (`deleteForgottenMemories`)、`export`、`memory list`、`memory remove` は `last_access` を進めません。
  - 活動行が無いスコープは `discount = 0`、`open_discount = 0` として現行曲線で計算します。活動行は最後のメモリ削除後も残します。
  - 起動ログ (`describeMemoryPolicy`) に、半減期のあいだアクセスが無いスコープはその後の忘却が 1/3 の速さになり残る期間はおよそ 3 倍までであることを 1 行追加します。

スコープの規則 (`internal/store/scope.go`) に、`branch` を 1 つ足します。

| 規則 | 内容 |
| --- | --- |
| 識別子 | リポジトリの単位とブランチがどちらも空でないときに、`<リポジトリの単位>:<ブランチ>` |
| 使えないときのエラー | `ErrNoBranch` |
| 範囲に入るセッション | リポジトリの単位とブランチがどちらも空でなく、その組が識別子と等しいセッション |
| ルームの置き場所 | ユーザーなし。`rooms.repository` に識別子 |

## 4. 受入条件

1. 同じリポジトリの単位と同じブランチを申告した、別のユーザー、別のマシンのセッションどうしが、`scope: "branch"` のルームと宛先で、メッセージをやりとりできる。
2. 同じリポジトリの別のブランチのセッションには、ブランチのルームのメッセージが届かない (未読にならない)。`scope: "repository"` のメッセージは、今のとおり、リポジトリの全員に届く。
3. ブランチの申告、そろえ方、エラー、置き換えが、2.2 のとおりに動作する。
4. ブランチのスコープを使えないセッションは、2.3 のエラーの案内を受ける。
5. ブランチのスコープのメモリは、同じ識別子のスコープを使えるセッションだけが読み書きできる。
6. `lounge_who`、`session list`、`memory list --scope branch`、書き出しが、2.5 のとおりに動作する。
7. 版 6 のデータベースが版 7 に移行し、ルーム、メッセージ、メモリの行と ID、メモリの ID の採番が保たれる。
8. `user` と `repository` のスコープの今のテストが、スコープの種類の列挙と案内文の上限を確かめるものを除き、変更なしで通る。
9. `lounge_help` の本文が、2.6 の内容を含み、19,000 バイト以下である。
10. `go vet ./...` と `go test -race ./...` が通る。
11. 5 章の実機の確認の結果が、確認の記録と、文書の「検証済みの範囲」に、検証済 / 未検証で書かれている。

## 5. 確認

### 5.1. 自動テスト

`go vet ./...`、`go test -race ./...`。足すテストは、次のとおりです。

- `profile.Branch`: 2.2 の規則の各行、Git が許す名前 (`feature/日本語`、`a@b`、`a#b`)。
- `lounge_join`: 2.2 の置き換えの表の各行、出力の `branch` と `hint`。
- スコープの規則: 使えるスコープと共有するスコープ、ブランチのルームへの送信の届き先 (同じブランチ、別のブランチ、別のリポジトリの同じ名前のブランチ、別のユーザー)、使えないときのエラー、ブランチを切り替えた後の届き先。
- メモリ: ブランチのスコープでの作成、検索、別のブランチからは「ない」と報告されること、スコープごとの上限。
- 移行: 版 6 のデータ (3 つのテーブルの行、削除済みの最も大きい ID のメモリ) を持つデータベースの、版 7 への移行。
- 案内文: 上限と、ブランチの案内の記載。
- 管理コマンドと書き出し: `BRANCH` の列、`--scope branch`、`branch-<識別子>` のフォルダー。

### 5.2. 実機 (WSL の側)

確認用のサーバーをループバックで起動し、確認用のデータベースと Git のリポジトリを、セッション用の一時フォルダーに置きます。5 つの CLI (Claude Code、Codex、Copilot CLI、Grok、agy) を、非対話で実行します (各 1 回。失敗した場合は 3 回まで)。相手役は、HTTP で直接ツールを呼ぶ方法で操作します。

| 項目 | 確かめること |
| --- | --- |
| a | 使い方の案内に従って参加し、`lounge_join` の出力の `branch` が、`git branch --show-current` の出力 (小文字) と合う |
| b | ブランチのルームで、同じブランチの相手役と 1 往復できる。別のブランチの相手役には届かない |
| c | `git switch` でブランチを切り替えた後に、`lounge_join` を呼び直し、記録の `branch` が変わる |

### 5.3. 実機 (Windows の側)

Windows の側のセッションに委譲します。

| 項目 | 確かめること |
| --- | --- |
| d | PowerShell を使う CLI が、案内に従ってブランチを申告する |
| e | ブランチ `main` があるリポジトリで、大文字と小文字を変えた名前 (`Main`) に切り替えたときの、`git branch --show-current` の出力と、サーバーが記録する値 |
| f | 同じブランチを申告した WSL の側のセッションと、ブランチのルームで 1 往復できる |

Windows の側のセッションが使えない場合、または CLI の利用量が足りない場合は、作業を止めて、利用者に扱いを確認します。確かめなかった項目は、文書に「未検証」と書きます。

## 6. 制限事項 (文書に書く内容)

- ブランチは、申告の値です。ブランチを切り替えた後に `lounge_join` を呼び直さないセッションは、前のブランチの範囲に残ります。
- ローカルのブランチの名前で比べます。同じリモートのブランチを、クローンごとに別のローカルの名前で扱うと、別の範囲になります。
- 大文字と小文字を区別しません。大文字と小文字だけが違う 2 つのブランチは、同じ範囲になります。
- ブランチにいないセッション (detached HEAD)、リポジトリの単位が空のセッションは、ブランチのスコープを使えません。
- ブランチの内容は引き継がれません。ブランチが使われなくなると、そのメモリは誰からも読めず、忘却で削除されます (固定したメモリは残ります)。マージの後も使う知見は、`repository` のスコープか、リポジトリの文書に保存します。
- 自分が申告していないブランチの内容を読む手段は、ありません。

## 7. 作業の進め方

### 7.1. 作業ブランチ

`main` から作業ブランチ `feature/branch-scope` を作り、作業前の記録 (この案件の記録と、前の案件の記録の `docs/prompts/past/` への移動) を最初のコミットにします。作業の途中で、作業ブランチを GitHub に push します。成果物の承認を受けたら、`main` にマージして push し、作業ブランチを消します。

### 7.2. 担当

| 担当 | 作業 |
| --- | --- |
| 実装の担当 (下の優先の順で決める) | 3 章の成果物の実装とテスト、文書の更新、5.2 の実機の確認の実行、実装のレビュー |
| このセッション (Claude Code、Fable) | 実装の担当への指示、結果の点検 (差分の確認、`go vet` と `go test` の実行)、Windows の側のセッションへの委譲、記録 (全体管理文書、簡易 ADR、残課題一覧、確認の記録)、コミット、成果物の提示 |
| Windows の側のセッション | 5.3 の確認 (モデルは、利用者が Windows の側で決める) |

実装の担当の優先の順は、次のとおりです。

| 時点 | 1 番目 | 2 番目 | どちらも使えないとき |
| --- | --- | --- | --- |
| 2026-11-22 10:50 JST まで | Grok (`grok -p`、モデル `grok-4.7`、推論の強さ high、操作は自動で許可) | agy | Claude Code のサブエージェント (難しい作業は Opus、易しい作業は Sonnet) |
| その後 | agy (`agy -p --dangerously-skip-permissions`、モデル `claude-sonnet-5-5-high`) | Grok | 同じ |

「使えない」は、利用量の上限に達して実行できない場合です。実装の担当は、コミットと push をしません。このセッションが、結果を点検してからコミットします。

> [!IMPORTANT]
> 利用者の指示にない点を、次のとおりに決めています。承認の際に、あわせて確認を受けます。
>
> - agy で使う Sonnet 5.5 の推論の強さは、high とします (agy の選択肢は low、medium、high)。
> - 優先するほうだけが使えない場合は、もう一方を使います。
> - 実装のレビューは、実装した担当とは別の担当 (上の表の 2 番目。使えなければこのセッション) が行います。

### 7.3. 手順

1. 作業ブランチの作成と、最初のコミット (7.1)。
