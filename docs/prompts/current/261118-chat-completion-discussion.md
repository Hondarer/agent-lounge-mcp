ユーザーが明示した内容は、次のとおりです (対話での指示)。

企画提案書で確認したことは、次のとおりです。

- 配信の状態は、`queued`、`delivered`、`acked`、`expired` の 4 つです。`chat_ack` は「メッセージを処理したことを記録します」、`chat_status` は「送ったメッセージの送達状態を確認します」、`chat_history` は「ルームまたは相手との過去のやりとりを読みます」と定めています。
- チャットの保存期限は、未確定の事項です。提案は、「`acked` から 30[日]、未取得のまま 14[日] で `expired`」です。
- 「`lounge_join` と `lounge_who` 以外のツールは、`scope` の引数を持ちます」と定めています。

現在の実装で確認したことは、次のとおりです。

- `deliveries` テーブル (版 1) は、状態の列に 4 つの値を許し、`delivered_at`、`acked_at`、`expired_at` の列を持ちます。使っているのは、`queued` と `delivered`、`delivered_at` だけです。送達の確認と期限切れのために、スキーマを変える必要はありません。
- `chat_inbox` は、`queued` の配信を古い順に返し、`delivered` にします。各メッセージを 1 回だけ返します。
- 未読の件数は、`queued` の配信の数です。すべてのツールの応答に付記します。
- `messages` と `deliveries` は、セッションを参照する外部キーに、連鎖の削除 (`ON DELETE CASCADE`) を定めています。セッションを削除すると、そのセッションが送ったメッセージと、そのセッション宛ての配信が削除されます。
- セッションは、最後の利用の時刻 (`last_seen_at`) を持ちます。ツールを呼ぶたびに更新します。
- 管理コマンドは、`user add`、`list`、`rotate`、`remove` です。セッションとメッセージを扱う管理コマンドは、ありません。
- サーバーの中に、定期的に動く処理は、ありません。
- 送信者の OS のユーザー名とマシンの名前は、`messages` に保存していません。`chat_inbox` は、取得の時点の送信者のセッションの値を返します (BL-029 の 1 番)。
