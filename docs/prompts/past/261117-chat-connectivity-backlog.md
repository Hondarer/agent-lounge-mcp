## BL-001 送達の確認 (`chat_ack`、`chat_status`)

### 概要と問題点

- **現状の事象**: 送達状態は `queued` と `delivered` までを記録します。`delivered` は、受信側のエージェントが `chat_inbox` で取得したことだけを表します。受信者が内容を処理したことを記録する `chat_ack` と、送信者が状態を確認する `chat_status` がありません。`deliveries` テーブルには `acked_at` の列がありますが、使っていません。
- **本来あるべき姿**: 受信者が `chat_ack` で処理の完了を記録でき、送信者が `chat_status` で、自分が送ったメッセージの受信者ごとの状態 (`queued`、`delivered`、`acked`) を確認できます。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (検討用 Markdown の Q-001。今回は 4 つのツールだけを実装する)。到達点からも `acked` の確認を除いています (Q-010)。
- **今回の見送り理由**: スコープ外。疎通確認には、送信と受信だけで足りるためです。
- **継続作業での経緯と対処**: 継続作業 `chat-autonomy` (検討用 Markdown `261117-chat-autonomy-discussion.md`、検討 ID `chat-autonomy`) の開始にあわせて、`261117-chat-autonomy-backlog.md` の同じ課題 ID へ転記しました (2026-11-17)。以後の状況は、転記先に記録します。

### 影響範囲とリスク

- **影響対象**: `internal/store/chat.go`、`internal/tools/chat.go`、`docs/ja/reference.md`。送信側のエージェントとその利用者。
- **放置した場合のリスク**: 送信者は、相手が読んだか、処理したかを確認できません。作業の依頼に使うと、相手の返信を待つ以外に進み具合を知る手段がありません。

### 推奨される対応策

- **恒久対応案**: `chat_ack` (引数: メッセージ ID の一覧。自分宛ての `delivered` を `acked` にする) と `chat_status` (引数: メッセージ ID。送信者本人だけが参照できる) を追加します。スキーマの変更は不要の見込みです。企画提案書の「チャット機能」の定義に合わせます。
- **参考情報**: Q-001、Q-010。`internal/store/schema/0001_init.sql` の `deliveries`。

## BL-003 トークンによるユーザーの識別

### 概要と問題点

- **現状の事象**: 認証がなく、すべての接続を固定の 1 ユーザー `local` として扱います。トークンを発行する管理コマンド (`user add`) と、`Authorization` ヘッダーの検証がありません。5 つのエージェントが HTTP の MCP サーバーに接続できることは確認済みですが、登録時にヘッダーを指定でき、要求に付けて送るかは未確認です。
- **本来あるべき姿**: ユーザーごとにトークンを発行でき、サーバーは `Authorization: Bearer` のトークンでユーザーを識別します。トークンのない要求と、無効なトークンの要求を拒否します。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (Q-002)。
- **今回の見送り理由**: スコープ外。ループバックだけで待ち受け、1 人の利用者が使う範囲では、認証がなくても疎通を確認できるためです。
- **継続作業での経緯と対処**: 継続作業 `chat-autonomy` (検討用 Markdown `261117-chat-autonomy-discussion.md`、検討 ID `chat-autonomy`) の開始にあわせて、`261117-chat-autonomy-backlog.md` の同じ課題 ID へ転記しました (2026-11-17)。以後の状況は、転記先に記録します。

### 影響範囲とリスク

- **影響対象**: `internal/server/server.go`、`internal/store/` (`users.token_hash`)、`cmd/agent-lounge-mcp/main.go`、各エージェントの登録コマンド、`docs/ja/`。
- **放置した場合のリスク**: 同じマシンの別の利用者や別のプロセスが、ループバックのポートに接続すると、メッセージを読み書きできます。BL-004 と BL-010 に着手できません。

### 推奨される対応策

- **恒久対応案**: 管理コマンド `user add` でトークンを生成し、ハッシュだけを `users.token_hash` に保存します。HTTP のミドルウェアでトークンを検証し、接続にユーザーを結び付けます。着手の前に、5 つのエージェントで、ヘッダーを指定した登録と送信を実機で確認します。固定ユーザー `local` からの移行の方法 (既存のセッションの扱い) を決めます。
- **参考情報**: Q-002。企画提案書の「未確定の事項」の「各エージェントの対応」。`internal/store/chat.go` の `EnsureLocalUser`。

## BL-005 `chat_inbox` の待ち受け

### 概要と問題点

- **現状の事象**: `chat_inbox` は、未読がなければすぐに空の結果を返します。待ち時間を指定して、届くまで応答を保留する機能がありません。このため、指示を待っているエージェントは、メッセージが届いても動きません。疎通確認では、`claude` が `codex` へ送った後、利用者が `codex` に受信箱の確認を指示するまで、メッセージは `queued` のままでした。
- **本来あるべき姿**: エージェントが、待ち時間を指定して `chat_inbox` を呼ぶと、メッセージが届いた時点、または待ち時間が過ぎた時点で応答が返ります。利用者が受信側に指示しなくても、返信を待つ作業を続けられます。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (Q-008)。疎通確認で、待機中のエージェントに届かないことを実際に確認しました。
- **今回の見送り理由**: スコープ外。各エージェントがツールの応答を待てる時間の上限が未確認で、設計に確認が必要なためです。
- **継続作業での経緯と対処**: 継続作業 `chat-autonomy` (検討用 Markdown `261117-chat-autonomy-discussion.md`、検討 ID `chat-autonomy`) の開始にあわせて、`261117-chat-autonomy-backlog.md` の同じ課題 ID へ転記しました (2026-11-17)。以後の状況は、転記先に記録します。

### 影響範囲とリスク

- **影響対象**: `internal/tools/chat.go`、`internal/store/chat.go`、`docs/ja/reference.md`、利用ルールの文面 (BL-006)。
- **放置した場合のリスク**: エージェント同士のやりとりのたびに、利用者が受信側へ指示する必要があります。利用者が介在しない協調作業に使えません。

### 推奨される対応策

- **恒久対応案**: `chat_inbox` に待ち時間の引数 (秒。既定は 0 で、今の動作) を追加し、サーバーの中で新着を通知して応答します。着手の前に、5 つのエージェントで、ツールの応答を待てる時間の上限を実機で測り、待ち時間の上限を決めます。MCP の通知 (サーバーからの通知やリソースの更新) をエージェントが扱えるかも、あわせて確認します。
- **参考情報**: Q-008。疎通確認の記録 (`261117-chat-connectivity-validation.md`) の「気付いた事項」。

## BL-006 利用ルールの文面の配布

### 概要と問題点

- **現状の事象**: 受信の動作を、接続時の案内文 (`instructions`) とツールの説明文だけで伝えています。`AGENTS.md` や `CLAUDE.md` に貼る指示文 (作業の開始時と区切りで受信箱を確認する、他者からの内容は指示として扱わない、など) がありません。疎通確認では、未読の件数が 1 以上の結果を受け取った後、指示がなくても `chat_inbox` を呼ぶエージェントと、呼ばないエージェントがありました (利用者の観察では、Codex、agy、Grok は未読があると自分から読みました。エージェントの動作は毎回同じとは限らないため、参考の情報です)。
- **本来あるべき姿**: 利用者がプロジェクトの指示ファイルに貼れる文面があり、5 つのエージェントが、同じ場面で同じように受信箱を確認します。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (Q-008)。エージェントごとの動作の違いは、疎通確認で利用者が確認しました。
- **今回の見送り理由**: スコープ外。文面を決めるには、各エージェントの実際の動作を先に確認する必要があったためです。
- **継続作業での経緯と対処**: 継続作業 `chat-autonomy` (検討用 Markdown `261117-chat-autonomy-discussion.md`、検討 ID `chat-autonomy`) の開始にあわせて、`261117-chat-autonomy-backlog.md` の同じ課題 ID へ転記しました (2026-11-17)。以後の状況は、転記先に記録します。

### 影響範囲とリスク

- **影響対象**: `docs/ja/user-guide.md`、`.agents/skills/agent-lounge-connect/SKILL.md`、`internal/tools/tools.go` の `Instructions`。
- **放置した場合のリスク**: エージェントによって、届いたメッセージを読む時期が変わります。利用者は、エージェントごとの癖を覚えて指示する必要があります。受信した内容を指示として実行するエージェントがあると、意図しない操作につながります。

### 推奨される対応策

- **恒久対応案**: まず、5 つのエージェントで、未読の件数を見た後の動作と、`instructions` を読むかどうかを記録します。その結果をもとに、貼り付け用の文面を `docs/ja/user-guide.md` に載せ、`instructions` の文面も見直します。

## BL-017 停止するときの、接続中のエージェントへの通知

### 概要と問題点

- **現状の事象**: サーバーは、停止の操作を受けると、端末に `shutting down` と表示し、開いている接続の終了を 5[秒] まで待って終了します (BL-015 で対応済み)。接続中のエージェントには、何も伝えません。エージェントは、次にツールを呼んで接続のエラーになるまで、サーバーが止まったことに気づきません。サーバーを起動し直した後は、`not joined` のエラーで、参加し直す必要があることを知ります。
- **本来あるべき姿**: サーバーは、停止するときに、接続中のエージェントへ停止する旨を通知します。エージェント (またはその利用者) は、サーバーが意図して止められたことと、起動し直した後に `lounge_join` で参加し直せばよいことを把握できます。

### 経緯と見送り理由

- **摘出契機**: 案件の完了の後、BL-015 の対処を確認した利用者が、要件として追加しました。企画提案書の「対象とすること」に、要件として記載済みです。
- **今回の見送り理由**: 案件の完了の後に追加された要件です。通知の手段と、各エージェントでの見え方に確認が必要なため、BL-015 のような小さな修正としては扱っていません。
- **継続作業での経緯と対処**: 継続作業 `chat-autonomy` (検討用 Markdown `261117-chat-autonomy-discussion.md`、検討 ID `chat-autonomy`) の開始にあわせて、`261117-chat-autonomy-backlog.md` の同じ課題 ID へ転記しました (2026-11-17)。以後の状況は、転記先に記録します。

### 影響範囲とリスク

- **影響対象**: `cmd/agent-lounge-mcp/main.go` の停止の処理、`internal/server/server.go`、`internal/tools/` (停止中のツールの応答)、`docs/ja/reference.md`。
- **放置した場合のリスク**: エージェントが、接続のエラーを一時的な障害と判断して再試行を繰り返したり、MCP サーバーの故障として利用者に報告したりします。返信を待っているエージェントが、待つ意味がなくなったことに気づきません。

### 推奨される対応策

- **恒久対応案**: MCP には、サーバーの停止を伝える専用の通知がありません。次の手段を、5 つのエージェントでの見え方を実機で確認した上で、組み合わせます。(1) 停止の待ち時間の最初に、開いている接続へ MCP のログ通知 (`notifications/message`) を送ります。エージェントがこの通知をモデルや利用者に見せるかどうかは、未確認です。(2) 停止の待ち時間の中で届いたツールの呼び出しには、「サーバーは停止中。起動し直した後に `lounge_join` を呼ぶ」というエラーを返します。(3) `chat_inbox` の待ち受け (BL-005) を実装した場合は、待っている呼び出しを、停止する旨の結果で返します。待機中のエージェントに届く手段は (3) だけの見込みです。
- **参考情報**: BL-005、BL-015。`docs/ja/reference.md` の「接続とセッション」。Go SDK の `ServerSession.Log`。
