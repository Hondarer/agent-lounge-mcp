# 対話の画面での検証の基盤と、待機中のエージェントへの通知 最終仕様

ファイル名: `261118-interactive-verification-design.md`

## 目的と到達点

各エージェントの CLI の対話の画面を、利用者の手作業なしに操作して確認できる基盤を作ります。その基盤で、これまで未検証だった、対話の画面での動作を確かめます。

到達点は、次の 6 つです。

| 番号 | 到達点 |
| --- | --- |
| 1 | 基盤が、2 つの OS (Linux と WSL、Windows) で、5 つの CLI の対話の画面を起動し、指示を送り、応答の完了を判定し、終了できます |
| 2 | サーバーが、接続の診断を出力でき、各 CLI が停止のログ通知を受け取る条件を満たすかどうかを切り分けられます |
| 3 | 対話の画面での 3 つの動作 (停止のログ通知の見え方、複数回のやりとり、起動し直した後の再参加) の結果が、CLI と OS ごとに記録されています |
| 4 | 接続時の案内文を CLI がモデルに渡すかどうかと、指示ファイルに貼る文面の効果が、CLI と OS ごとに記録されています |
| 5 | ログ通知の代わりになる手段の調査の結果が、記録されています |
| 6 | 401 を受けたときの動作が、未検証の 3 つの CLI で記録され、`chat-probe.sh` が確認の後にメッセージを残しません |

> [!IMPORTANT]
> 到達点 5 の調査で、使える手段が見つかった場合は、製品への実装の前に、作業を止めて利用者に確認します ([通知の改善の実装](#通知の改善の実装))。この最終仕様は、調査までを定めます。

## 範囲

### 今回実装すること

- 検証の基盤 (`scripts/interactive/`)。開発とテストのための道具です。
- サーバーの起動オプション `--log-connections` (接続の診断の出力)。
- `chat-probe.sh` の修正 (確認の最後に、残したメッセージの完了を記録する)。
- 基盤を使った確認と、その記録。
- 文書の更新 (`docs/ja/interactive-verification.md` の新規作成を含む)。

### 今回実装しないこと

| 事項 | 扱い |
| --- | --- |
| ツールの許可の画面の確認 | 確認しません。残課題に残します |
| 案内文に文を足す起動オプション | 加えません。案内文の確認は、一時フォルダーで作る確認用の実行ファイルで行います |
| サーバーからの問い合わせ (elicitation) を使った通知 | 調べません |
| 通知の改善の、製品への実装 | 調査の結果を見て、利用者に確認してから決めます |
| 基盤の CI での実行 | 行いません。各 CLI のログインと利用量が要るためです。基盤の自己試験のうち、CLI を使わないものだけを CI に加えます |
| macOS での確認 | 行いません。未検証と書きます |

## 接続の診断の出力

### 起動オプション

`serve` に、`--log-connections` (値なし。既定は無効) を加えます。有効にすると、MCP の接続ごとに、次の行を標準エラーに出力します。無効のときの出力は、これまでと変わりません。

| 出力する時点 | 行の形式 |
| --- | --- |
| 接続の初期化が終わったとき | `connection <番号>: initialized client="<名前>" version="<版>" protocol=<プロトコルの版>` |
| 要求を受けたとき | `connection <番号>: request <メソッド>`。ツールの呼び出しでは、`connection <番号>: request tools/call <ツール名>` |
| ログのレベルが設定されたとき | `connection <番号>: log level <レベル>` |
| 停止の通知を送ったとき | `connection <番号>: shutdown notice sent` |
| 停止の通知を送らなかったとき | `connection <番号>: shutdown notice not sent (the client set no log level)` |
| 停止の通知の送信に失敗したとき | `connection <番号>: shutdown notice failed` |

各行の先頭には、他の診断の出力と同じ日時が付きます。

### 出力する値の規則

- `<番号>` は、サーバーの起動からの通し番号 (1 から) です。MCP のセッション ID は、接続を引き継げる値のため、出力しません。
- クライアントの名前と版は、クライアントが送った値です。制御文字と引用符を取り除き、64 文字で切ります。
- ツールの呼び出しは、ツールの名前だけを出力します。引数、結果、メッセージの本文、メモリの内容、トークン、ユーザー名、セッション名は、出力しません。
- 通知 (応答を求めないメッセージ) のうち、出力するのは `notifications/initialized` だけです。

> [!NOTE]
> ツールの名前を出力するのは、エージェントが、いつ `lounge_join` や `chat_inbox` を呼んだかを、サーバーの側から確かめるためです。画面の出力からツールの呼び出しを読み取る方法は、CLI ごとに表示が異なり、不確かです。

### 実装

- `internal/config/` に、設定の項目を加えます。`cmd/agent-lounge-mcp/` で、オプションを読みます。
- `internal/server/` で、SDK の受信のミドルウェアを使い、要求のメソッド、ツール名、`logging/setLevel` を記録します。接続の番号は、サーバーの中で接続ごとに割り当てます。
- 停止の通知の結果は、`BeginShutdown` の中で、接続ごとに出力します。ログのレベルを設定していない接続には、SDK が通知を送らないため、「送らなかった」と出力します。

## 検証の基盤

### 位置づけ

基盤は、このリポジトリの開発とテストのための道具です。配布物 (`dist/` の実行ファイル、スキル) には含めません。

### 前提

| OS | 必要なもの |
| --- | --- |
| Linux、WSL | Python 3.10 以降 (標準ライブラリだけを使います)、確認する CLI、サーバーの実行ファイル |
| Windows | Python 3.10 以降、ライブラリ `pywinpty` (仮想端末の機能 ConPTY を使うため)、確認する CLI、サーバーの実行ファイル (`windows-amd64`) |

基盤は、OS ごとに、その OS の Python で、独立して動きます。Windows の側の確認に、WSL は要りません。

### モジュールの構成

共通の部分と、OS に固有の部分を分けます。OS に固有の部分は、仮想端末を扱うモジュールと、プロセスへの信号の送り方だけです。同じ処理を、2 か所に書きません。

```text
scripts/interactive/
    verify.py              入口 (引数の解釈、シナリオの実行、結果の出力)
    harness/
        terminal.py        仮想端末の共通の型 (起動、書き込み、読み取り、大きさ、終了) と、OS による選択
        terminal_posix.py  Linux と WSL の実装 (標準の pty モジュール)
        terminal_windows.py  Windows の実装 (pywinpty)
        screen.py          出力の加工 (制御文字の除去)、文字列の待ち合わせ、時間切れ
        agents.py          CLI ごとの定義
        server.py          サーバーの起動と停止、接続の診断の読み取り、/healthz
        lounge.py          相手役のセッション (MCP を HTTP で呼ぶ、小さなクライアント)
        report.py          結果の記録 (JSON と、画面の出力の保存)
        scenarios/         シナリオごとのモジュール
    tests/
        fake_agent.py      自己試験用の、対話の画面を持つ小さなプログラム
        test_*.py          自己試験
```

スクリプトのコメント、使い方の表示、結果の項目名は、英語で書きます。

### CLI ごとの定義

`agents.py` に、CLI ごとに次の項目を定義します。値は、OS で異なる場合だけ、OS ごとに持ちます。

| 項目 | 内容 |
| --- | --- |
| 起動のコマンド | 対話の画面の起動。先に許可を与えるオプションを含みます |
| 非対話の起動のコマンド | 指示を 1 回だけ実行する起動 (401 の確認で使います) |
| 登録と解除のコマンド | 確認用のサーバーを、名前 `agent-lounge` で登録し、解除するコマンド |
| 入力の準備ができた目印 | 起動の後、指示を受け付ける状態になったことを示す文字列 |
| 入力の確定の方法 | 指示の文字列を送った後に送るキー |
| 終了の方法 | CLI を終了するキーまたはコマンド |
| 指示ファイルの名前 | その CLI が読む指示ファイル ([貼る文面の確認](#シナリオ-5-指示ファイルに貼る文面)) |

### 応答の完了の判定

対話の画面の出力は、制御文字を含み、同じ内容が何度も描き直されます。画面の内容を再現する端末エミュレーターは、使いません。次の方法で判定します。

- 指示のたびに、乱数の印を 2 つの部分に分けて渡し、「応答の最後に、2 つの部分をつないだ語を書く」ように求めます。画面に表示される指示の文には、つないだ語が現れないため、つないだ語が出力に現れたことで、応答の完了を判定できます。
- 制御文字を取り除いた出力に、目的の文字列があるかどうかだけを見ます。画面の上の位置や色は、見ません。
- 指示ごとに、時間の上限 (既定は 180[秒]) を設けます。上限までに印が現れない場合は、その確認の結果を「判定できない」とし、そこまでの出力を保存します。

### 許可とサンドボックス

確認用のフォルダーの中で、起動のオプションと設定で、先に許可を与えます。許可の画面には、応答しません。まず、個別の許可 (agent-lounge のツールと、確認用のフォルダーの中の読み書き) を試します。それで足りない CLI だけ、サンドボックスを外すオプションを使い、その旨を記録します。

### 確認用の環境

- 基盤は、実行のたびに、OS の一時フォルダーの下に、確認用のフォルダーを作ります。データベース、CLI の作業フォルダー、結果は、その中に置きます。リポジトリの中と `dist/` には、何も作りません。
- 基盤は、サーバーを、ループバックのアドレスと、既定とは別のポート (既定は `127.0.0.1:7799`) で起動します。サーバーの実行ファイルは、引数で指定します。
- CLI への登録は、確認の前に行い、確認の後に解除します。利用者の設定に、すでに `agent-lounge` の名前の登録がある CLI では、上書きせず、その CLI の確認を中止して報告します。
- 各 CLI は、既定の設定のモデルを使います。モデルの名前が画面や出力から分かる場合は、記録します。

### 結果の記録

基盤は、シナリオ、CLI、OS ごとに、1 つの結果を JSON で出力します。項目は、環境 (OS、CLI の版、サーバーの版)、手順ごとの判定、接続の診断から読み取った値、時間です。画面の出力は、制御文字を取り除いたものを、別のファイルに保存します。

結果と画面の出力は、確認用のフォルダーに置き、リポジトリには入れません。リポジトリに入れるのは、確認の記録 (`docs/prompts/current/261118-interactive-verification-validation.md`) にまとめた内容だけです。記録には、利用者の名前、コンピューターの名前、アドレス、トークンを書きません。

### 自己試験

- `tests/fake_agent.py` は、対話の画面を持つ小さなプログラムです (入力の待ち受けの表示、色付きの出力、描き直し、遅れのある応答)。
- 自己試験は、`fake_agent.py` を基盤で操作して、起動、指示、完了の判定、時間切れ、終了を確かめます。出力の加工と、接続の診断の読み取りも、試験します。
- 実行は、`python3 -m unittest discover -s scripts/interactive/tests` です (Windows では `python`)。
- CI (`.github/workflows/ci.yml`) に、Linux での自己試験を加えます。

## シナリオ

シナリオ 1 から 5 は、対話の画面で行います。5 つの CLI (Claude Code、Codex、Copilot CLI、Grok、agy) と、2 つの OS で行います。指示文は、英語で書き、確認の記録に載せます。

セッション名は、`iv-<CLI の短い名前>` の形です。相手役は、基盤が MCP を直接呼ぶセッション (`iv-peer`) です。

### シナリオ 1: 停止のログ通知

| 手順 | 内容 |
| --- | --- |
| 1 | `--log-connections` を付けてサーバーを起動し、CLI を起動します |
| 2 | 指示 1: ラウンジに参加して、参加できたことを報告する |
| 3 | 応答の完了の後、指示を待つ状態のまま、サーバーに停止の信号を送ります |
| 4 | 20[秒] の間、画面の出力を記録します |
| 5 | 指示 2: ツールを呼ばずに、前の応答の後に agent-lounge のサーバーから知らせを受け取ったかどうかと、その内容を答える |

記録する項目は、次のとおりです。

| 項目 | 値 | 判定の方法 |
| --- | --- | --- |
| ログのレベルの設定 | 設定した、設定しなかった | 接続の診断 |
| 通知の送信 | 送った、送らなかった、失敗した | 接続の診断 |
| 画面への表示 | 見える、見えない | 手順 4 の出力に、停止の文面の一部 (`shutting down`) があるか |
| モデルへの伝達 | 伝わった、伝わらなかった、判定できない | 手順 5 の応答に、停止を示す内容があるか |

### シナリオ 2: 複数回のやりとり

| 手順 | 内容 |
| --- | --- |
| 1 | サーバーと CLI を起動します |
| 2 | 指示 1: ラウンジに参加して、参加できたことを報告する |
| 3 | 相手役が、このセッション宛てに、乱数の印を含むメッセージを送ります |
| 4 | 指示 2: 受信箱を確認して、届いたメッセージの本文を答える |

合格の条件は、手順 4 の応答に印があり、相手役から見た送達状態が、受け取り済みになっていることです。あわせて、接続の診断から、指示 1 と指示 2 が同じ接続で行われたかどうかを記録します (合格の条件には含めません)。

### シナリオ 3: 起動し直した後の再参加

| 手順 | 内容 |
| --- | --- |
| 1 | サーバーと CLI を起動します |
| 2 | 指示 1: ラウンジに参加して、参加できたことを報告する |
| 3 | CLI を終了します |
| 4 | 相手役が、このセッション宛てに、乱数の印を含むメッセージを送ります |
| 5 | CLI を起動し直します |
| 6 | 指示 2: 前と同じ名前でラウンジに参加し直して、受信箱のメッセージの本文を答える |

合格の条件は、手順 6 の応答に印があり、セッションが 1 つのまま (同じ名前のセッションが増えていない) であることです。

### シナリオ 4: 接続時の案内文

確認用の実行ファイルを使います。基盤は、リポジトリのソースを一時フォルダーに複製し、接続時の案内文の末尾に、合言葉を含む 1 文を足して、ビルドします。合言葉は、実行のたびに作る乱数の語で、ツールの説明文と `lounge_help` には現れません。Windows 向けの実行ファイルは、Go のある環境でクロスビルドし、Windows の側の基盤に、引数で渡します。確認用の実行ファイルは、コミットせず、配布しません。

| 手順 | 内容 |
| --- | --- |
| 1 | 確認用の実行ファイルでサーバーを起動し、指示ファイルのないフォルダーで CLI を起動します |
| 2 | 指示: ツールを呼ばずに、agent-lounge のサーバーが接続のときに伝えた合言葉を答える。知らない場合は `UNKNOWN` と答える |

| 応答 | 記録する結果 |
| --- | --- |
| 合言葉がある | 案内文をモデルに渡している |
| `UNKNOWN` がある | 案内文をモデルに渡していない |
| どちらもない、または時間切れ | 判定できない |

### シナリオ 5: 指示ファイルに貼る文面

**指示ファイルの名前の確認**: CLI ごとに、その CLI の文書が定める指示ファイルの名前を調べます。次に、確認用のフォルダーに、その名前のファイルを置き、合言葉を含む 1 文を書いて、シナリオ 4 と同じ方法 (合言葉を答えさせる) で、CLI がそのファイルを読むことを確かめます。確かめた名前を、`agents.py` の定義と、文書に書きます。

**文面の確認**: CLI ごとに、3 回行います。毎回、新しいフォルダー、新しいセッション名、新しい CLI のプロセスを使います。

| 手順 | 内容 |
| --- | --- |
| 1 | `--log-connections` を付けてサーバーを起動します |
| 2 | 新しいフォルダーに、確かめた名前の指示ファイルを置きます。内容は、`lounge_help` が返す文面で、`<name>` をセッション名に置き換えたものです |
| 3 | CLI を起動します |
| 4 | 指示: チャットとは関係のない、2 つの段階の作業 (ファイル `notes.txt` を作って 3 行を書く。次に、読み返して行数を答える) |

記録する項目は、次のとおりです。接続の診断のツール名と時刻、`notes.txt` の作成の時刻から判定します。

| 項目 | 判定の方法 |
| --- | --- |
| 参加したか | `lounge_join` の呼び出しがある |
| 開始時に受信箱を確認したか | `notes.txt` の作成より前に、`chat_inbox` の呼び出しがある |
| 区切りで受信箱を確認したか | `notes.txt` の作成より後に、`chat_inbox` の呼び出しがある |
| 開始時にメモリを検索したか | `memory_search` の呼び出しがある |

この確認は、合格と不合格を付けません。CLI と OS ごとに、3 回のうち何回行ったかを記録します。

### シナリオ 6: 401 を受けたときの動作

非対話の実行で行います。対象は、Codex、Copilot CLI、agy で、2 つの OS で行います。

| 手順 | 内容 |
| --- | --- |
| 1 | `--require-token` を付けてサーバーを起動し、確認用のユーザーを追加して、トークンを付けて CLI に登録します |
| 2 | 指示 1: ラウンジに参加して報告する (参加できることを確かめます) |
| 3 | 管理コマンドで、トークンを再発行します (CLI の持つトークンが無効になります) |
| 4 | 指示 2: ラウンジに参加して報告する。時間の上限は 180[秒] です |

記録する項目は、利用者への報告に、認証の失敗 (401 またはトークン) が含まれるか、OAuth の認証の流れを始めたか、時間の上限までに終わったか、です。合格と不合格は付けません。確認の後、登録を解除し、トークンが CLI の設定と履歴に残っていないかを調べて、残っている場合は記録します。

## 他の通知の手段の調査

停止のログ通知が、指示を待っている状態の利用者にもモデルにも伝わらない CLI があった場合に、代わりの手段を調べます。5 つの CLI のすべてで伝わった場合も、ログの機能が非推奨のため、調査は行います。

調査は、一時フォルダーで作る試作のサーバー (コミットしません) と、基盤で行います。

| 手段 | 試作の内容 | 見る項目 |
| --- | --- | --- |
| ツールの一覧の変更通知 | 合図を受けると、説明文に知らせの文面を持つツールを 1 つ足す | 通知の後に、CLI がツールの一覧を取り直すか (接続の診断)。画面に表示されるか。次の指示で、モデルが、ツールを呼ばずに、新しいツールを知っているか |
| リソースの更新通知 | 未読の件数を表すリソースを公開し、合図を受けると更新を通知する | CLI がリソースを購読するか (接続の診断)。購読した場合、更新の後に読み直すか。画面に表示されるか |
| 各 CLI が持つ独自の通知の仕組み | 各 CLI の公開の文書で、サーバーからセッションへ知らせを入れる仕組みの有無と、仕様を調べる。仕様が公開されているものだけ、試作して確かめる | 仕組みの有無、条件、文書の場所。試作した場合は、画面とモデルへの伝わり方 |

試作のサーバーは、指示を待っている状態で知らせを送るための合図 (ループバックだけで受ける HTTP の要求) を持ちます。この合図は、試作だけのもので、製品には入れません。

「使える手段」は、指示を待っている状態で、利用者が画面で気づけるか、次の指示のときに、モデルがツールを呼ばずに知らせの内容を知っている手段です。1 つ以上の CLI で、これに当たる手段があれば、「見つかった」とします。

### 通知の改善の実装

- 使える手段が見つかった場合は、対象成果物への書き込みを止めて、調査の結果を利用者に示します。何をきっかけに、誰に、何を送るかを、追加の質問で決め、この最終仕様を改版して、承認を受けてから実装します。
- 見つからなかった場合は、待機中のエージェントに停止が伝わらないことを、制限として文書に書きます。企画提案書の要件の文面の見直しが必要かどうかは、成果物の提示のときに、利用者に確認します。
- 調査の結果と決定: 使える手段は、Claude Code のチャンネルだけでした。利用者に確認し、汎用の手段ではないため、実装しないことに決まりました (検討用 Markdown の Q-022。2026-11-19)。見つからなかった場合と同じく、制限として文書に書き、要件の文面の見直しを、成果物の提示のときに確認します。

## chat-probe.sh の修正

`.agents/skills/agent-lounge-connect/scripts/chat-probe.sh` は、`chat_history` の確認のために、完了を記録しないメッセージと、読まないメッセージを送ります。確認の最後に、受信側のセッションが、残りのメッセージを受け取り、完了を記録するようにします。その後、未完了の一覧に、この実行のメッセージが残っていないことを確かめます。

## 2 つの OS での実行

| 項目 | Linux、WSL | Windows |
| --- | --- | --- |
| 基盤を動かす Python | WSL の側の Python 3 | Windows の側の Python |
| サーバー | `dist/` の `linux-amd64` の実行ファイル | `dist/` の `windows-amd64` の実行ファイル (WSL の側でクロスビルド) |
| サーバーの停止 | `SIGINT` | Ctrl+Break の信号 (Go は、割り込みとして受け取ります) |
| CLI | WSL の側に導入したもの | Windows の側に導入したもの |

- Windows の側の Python に、`pywinpty` を導入します (`python -m pip install --user pywinpty`)。導入は、確認の後も残します。文書に、前提として書きます。
- Windows の側の作業は、Windows で動いている Claude Code のセッション (以下、Windows の側のセッション) が行います。WSL の側のセッション (実装を行うセッション) は、Windows のプログラムを起動しません。
- Windows の側のセッションが行う作業は、ブランチの取得 (`git pull`)、`pywinpty` の導入、自己試験の実行、シナリオ 1 から 6 の実行、CLI への登録と解除、後片付け、結果の報告です。
- WSL の側のセッションは、作業の依頼 (手順、実行するコマンド、報告してほしい項目) をセッション間のメッセージで送り、報告を確認の記録にまとめます。依頼と報告に、トークン、利用者の名前、コンピューターの名前を書きません。
- Windows の側には Go がないため、`windows-amd64` の実行ファイル (製品と、シナリオ 4 の確認用) は、WSL の側のセッションがクロスビルドし、Windows の側から読めるフォルダーに置きます。Windows の側のセッションは、それを Windows の側の一時フォルダーに複製して使い、確認の後に消します。
- 基盤の不具合が Windows の側で見つかった場合、修正は WSL の側のセッションが行ってプッシュし、Windows の側のセッションが取得し直します。Windows の側のセッションは、リポジトリのファイルを変更しません。
- Windows の側では、サーバーも Windows で動きます。これにより、Windows の側で起動したサーバーに、Windows の側のエージェントが接続する構成も、確認の対象になります。

> [!IMPORTANT]
> 次の場合は、作業を止めて、利用者に相談します。
>
> - `pywinpty` を導入できない、または、導入しても仮想端末を作れない場合。
> - Windows の側のセッションに、連絡がつかない場合。
> - どちらかの OS で、基盤で操作できない CLI が 3 つ以上になった場合。
>
> 操作できない CLI が 2 つ以下の場合は、その CLI を「未検証」とし、理由を記録して、残課題に残します。他の CLI の確認は進めます。

## 進め方

- ブランチ `feature/interactive-verification` で作業します。`main` へのマージは、成果物の承認の後、利用者の指示があった場合に行います。
- このセッションが実装し、サブエージェント (このセッションと同じモデル) が、実装をレビューします。Windows の側の実行は、Windows の側のセッションが行います ([2 つの OS での実行](#2-つの-os-での実行))。レビューの対象は、Go の変更と、基盤のスクリプトです。
- 確認の結果、手順、指示文、環境、気付いた事項は、`docs/prompts/current/261118-interactive-verification-validation.md` に記録します。
- 確認の後、CLI への登録を解除し、確認用のフォルダーを消します。2 つの OS で、無視の対象のフォルダーを含めて、残りがないことを確かめます。
